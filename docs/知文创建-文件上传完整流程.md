# 知文创建 & 文件上传完整流程

## 架构概览

系统采用**客户端直传 OSS + 后端元数据确认**模式。后端不直接接触文件字节，只负责生成预签名 URL 和记录元数据。

---

## 完整时序图

```
用户浏览器                      后端服务器                       阿里云 OSS
   |                               |                               |
   | 1. POST /knowposts/drafts --->|                               |
   |    (懒创建草稿)               |--INSERT know_posts            |
   |   <-- { id: "雪花ID" } ------|                               |
   |                               |                               |
   | 2. POST /storage/presign --->|                               |
   |    { scene, postId, type }    |--生成预签名 PUT URL            |
   |   <-- { putUrl, headers } ---|                               |
   |                               |                               |
   | 3. PUT putUrl (直传) ------------------------------------------------>|
   |    (文件字节直接到 OSS)       |                               |
   |   <-- ETag -------------------|                               |
   |                               |                               |
   | 4. PATCH /knowposts/{id} --->|                               |
   |    { title, tags, imgUrls }   |--UPDATE know_posts            |
   |   <-- 200 OK ----------------|                               |
   |                               |                               |
   | 5. POST /{id}/publish ------>|                               |
   |                               |--UPDATE status="PUBLISHED"   |
   |   <-- 200 OK ----------------|                               |
```

---

## 各阶段详解

### 阶段 1: 懒创建草稿

- **触发条件**: 用户选择图片上传时（非进入页面时立即创建）
- **目的**: 避免产生空草稿
- **数据库状态**: `status=DRAFT`, `visible=PRIVATE`, 其余字段为 NULL
- **返回**: 雪花 ID（字符串，防 JS 精度丢失）

### 阶段 2: 获取预签名 URL

预签名 URL 的本质：**让浏览器能绕过服务器，直接访问 OSS 的凭证**。

```
服务器（有阿里云 AccessKey）→ 签发 putUrl（有效期 10 分钟，绑定 Content-Type）
                              ↓
浏览器拿到 putUrl → 直接 PUT 文件到 OSS
```

**为什么需要预签名？**
- OSS 有访问控制，不能随便写入
- 预签名 = 临时授权凭证，像"临时门禁卡"
- 有时效 + 绑定 Content-Type，防止滥用
- 服务器只负责"开条子"，不负责"搬货"

**返回值**:
```json
{
  "objectKey": "posts/123/images/20260514/abc.jpg",
  "putUrl": "https://bucket.oss-cn-hangzhou.aliyuncs.com/posts/123/images/20260514/abc.jpg?Expires=...&Signature=...",
  "headers": {"Content-Type": "image/jpeg"},
  "expiresIn": 600
}
```

### 阶段 3: 客户端直传 OSS

浏览器直接用 `fetch PUT` 把文件字节发送到预签名 URL，后端服务器完全不参与文件传输。

### 阶段 4: 前端提交公网地址（数据库怎么知道地址？）

**关键点**: 数据库里的地址是前端上传完后告诉后端的，不是后端自己检测到的。

```
① 前端拿到预签名 URL
   putUrl = "https://bucket...abc.jpg?Expires=...&Signature=..."

② 前端 PUT 文件到 OSS（直传）

③ 前端从 putUrl 中截取公网地址（去掉 ? 后面的签名参数）
   publicUrl = putUrl.split("?")[0]
   → "https://bucket...abc.jpg"  （干净地址，长期有效）

④ 前端调用 PATCH /knowposts/{id}
   Body: { imgUrls: [publicUrl, ...] }

⑤ 后端把这个地址写入数据库 img_urls JSON 列
```

**两种 URL 的区别**:
| URL 类型 | 示例 | 用途 | 有效期 |
|---|---|---|---|
| 预签名 URL | `https://bucket...abc.jpg?Expires=...&Signature=...` | 直传 OSS | 10 分钟 |
| 公网 URL | `https://bucket...abc.jpg` | 存数据库，长期访问 | 永久 |

### 阶段 5: 可选 - 正文内容上传

如果用户写了富文本内容（Markdown），按同样流程：
1. 预签名（scene=`KnowPosts_content`）→ 生成 `posts/{postId}/content.md`
2. 前端 PUT 上传
3. 调用 `POST /{id}/content/confirm` 记录 objectKey / etag / size / sha256

### 阶段 6: 发布

调用 `POST /{id}/publish`，后端将 `status` 从 `DRAFT` 改为 `PUBLISHED`，设置 `publish_time`。

## 数据库表 `know_posts` 关键字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 雪花分布式 ID |
| `status` | VARCHAR(16) | 状态机: `DRAFT` → `PUBLISHED` |
| `visible` | VARCHAR(32) | 可见性: `PUBLIC` / `PRIVATE` / `FOLLOWERS` |
| `title` | VARCHAR(256) | 标题（最多 50 字符） |
| `description` | VARCHAR(50) | 摘要 |
| `tags` | JSON | 标签数组 `["Java","Spring Boot"]` |
| `img_urls` | JSON | 图片 URL 数组 |
| `content_url` | TEXT | 正文 OSS 公网 URL |
| `content_object_key` | VARCHAR(512) | 正文 OSS 对象键 |
| `content_sha256` | CHAR(64) | 正文 SHA-256 校验 |
| `creator_id` | BIGINT UNSIGNED | 创建者 ID |
| `is_top` | TINYINT(1) | 是否置顶 |
| `is_delete` | TINYINT(1) | 软删除标记 |
| `create_time` | TIMESTAMP | 创建时间 |
| `publish_time` | TIMESTAMP | 发布时间（草稿时为 NULL） |

## 设计亮点

1. **懒创建草稿**: 避免空草稿污染数据库
2. **客户端直传**: 文件不经过服务器，省带宽和内存
3. **预签名安全**: 有时效 + Content-Type 绑定，防滥用
4. **双重校验**: ETag + SHA-256，确保文件完整性
5. **雪花 ID**: 分布式唯一，返回字符串防精度丢失
6. **软删除**: `@TableLogic` 自动过滤已删除记录
