## 1. 认证双令牌模式

### 是什么？
双令牌就是登录后发**两个令牌**：
- **Access Token（短期令牌）**：15分钟有效，用来访问 API
- **Refresh Token（长期令牌）**：7天有效，专门用来"续命"——获取新的 Access Token

### 为什么需要两个令牌？
| 问题 | 单令牌 | 双令牌 |
|------|--------|--------|
| Token 被盗 | 长期有效，风险大 | Access Token 15分钟就过期，风险小 |
| 用户体验 | 每15分钟要重新登录 | 自动续命，用户无感知 |
| 安全性 | 频繁传输长 Token |  Refresh Token 只在续命时用一次 |

### 核心流程图

```
用户登录
   │
   ▼
┌─────────────────────────────────┐
│  服务端同时生成两个令牌：          │
│  Access Token (15min)            │
│  Refresh Token (7天)             │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  Refresh Token 存入 Redis 白名单 │
│  key: auth:rt:{userId}:{jti}    │
│  value: "1"                     │
│  TTL: 7天                       │
└─────────────────────────────────┘
   │
   ▼
返回给前端两个令牌

访问 API 时：
   │
   ▼
┌─────────────────────────────────┐
│  带 Access Token 访问            │
│  过期 → 用 Refresh Token 续命    │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  续命流程（Token Rotation）：      │
│  1. 验证 Refresh Token           │
│  2. 检查 Redis 白名单            │
│  3. 生成新的一对令牌              │
│  4. 删除旧的 Refresh Token       │
│  5. 存入新的 Refresh Token       │
│  返回新令牌                      │
└─────────────────────────────────┘
```

### 关键代码位置
- 配置类：`auth/config/AuthProperties.java`
- 令牌生成：`auth/token/JwtService.java`
- Redis 白名单：`auth/token/RedisRefreshTokenStoreImpl.java`

### 面试常问
**Q: 为什么用 RS256（RSA非对称加密）而不是 HS256（对称加密）？**
A: RS256 的私钥只在服务端，公钥可以分发。即使公钥泄露，攻击者也无法伪造 Token。HS256 的密钥双方都有，泄露风险更高。

**Q: 登出时为什么只删 Refresh Token，不删 Access Token？**
A: Access Token 只有15分钟有效期，过期自然失效。专门维护一个 Token 黑名单成本太高，不值得。

## 2. 渐进式发布流程

### 是什么？
渐进式发布 = **分步保存**，不是一次性提交所有内容。就像写作文，先写草稿，再补内容，最后正式发布。

### 流程详解

```
步骤1: 创建草稿
   │  POST /api/v1/knowposts/drafts
   │  只传 creatorId，其他都不用填
   │  自动生成 Snowflake ID
   │  状态: DRAFT
   ▼
步骤2: 上传内容（前端直传 OSS）
   │  前端获取预签名 URL
   │  直接 PUT 上传到阿里云 OSS
   │  服务端不需要代理上传！
   ▼
步骤3: 确认上传
   │  POST /api/v1/knowposts/{id}/content/confirm
   │  告诉服务端：文件已上传，这是 objectKey、etag、size、sha256
   ▼
步骤4: 补充元数据
   │  PATCH /api/v1/knowposts/{id}
   │  设置标题、标签、封面图、可见范围
   ▼
步骤5: 正式发布
   │  POST /api/v1/knowposts/{id}/publish
   │  状态: DRAFT → PUBLISHED
   ▼
完成！
```

### 为什么这样设计？
| 优势 | 说明 |
|------|------|
| **减轻服务端压力** | 文件直传 OSS，不经过服务端，节省带宽 |
| **支持断点续传** | 草稿已保存，网络中断后可以从步骤3继续 |
| **用户体验好** | 写到一半可以保存，不用一次写完 |
| **支持 AI 摘要** | 发布时可以调用 DeepSeek 生成描述 |

### 关键代码位置
- 草稿创建：`knowpost/service/impl/KnowPostServiceImpl.java`
- OSS 上传：`storage/OssStorageService.java`

## 3. Outbox 事件驱动模式（用户关系）

### 是什么？
Outbox 模式 = **业务写入和事件发布保证原子性**。确保"数据库写成功"和"事件发送成功"要么同时发生，要么同时失败。

### 为什么需要 Outbox？

**问题场景**：用户关注了某人
- 数据库写入成功 ✓
- Kafka 事件发送失败 ✗
- 结果：数据库有记录，但下游服务（如计数器）不知道这件事！

**解决办法**：把"要发的事件"也写到数据库的 outbox 表里，让 Canal 监听 binlog 把它捞出来发到 Kafka。

### 完整流程

```
用户点击"关注"
   │
   ▼
┌─────────────────────────────────┐
│  @Transactional 开启事务        │
│  1. 写入 following 表           │
│  2. 写入 outbox 表（同事务）     │
│     payload = FollowCreated事件  │
│  事务提交（两条记录同时生效）     │
└─────────────────────────────────┘
   │
   ▼
Canal 监听 MySQL binlog
   │  订阅 outbox 表的 INSERT 事件
   ▼
┌─────────────────────────────────┐
│  CanalKafkaBridge               │
│  TCP连接 Canal → 解析binlog      │
│  提取 payload → 发到 Kafka       │
│  topic: canal-outbox            │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  CanalOutboxConsumer 消费       │
│  解析 RelationEvent             │
│  更新计数器、缓存等             │
└─────────────────────────────────┘
```

### 关键代码位置
- Outbox 写入：`common/OutboxMessageUtil.java`
- Canal 桥接：`outbox/CanalKafkaBridge.java`
- 消费者：`outbox/CanalOutboxConsumer.java`

### 面试常问
**Q: 为什么不直接用 Kafka 发事件，还要用 Outbox？**
A: 直接发 Kafka 和写数据库是两个操作，无法保证原子性。如果数据库写成功但 Kafka 发送失败，数据就会不一致。Outbox 把事件写到数据库，Canal 通过 binlog 监听，保证了"写入即发布"。

**Q: Canal 是什么？**
A: Canal 是阿里开源的 MySQL binlog 增量订阅组件。它伪装成 MySQL 从库，实时监听 binlog 变化，把数据变更事件推送给下游。

## 4. 定制化 Redis SDS

### 是什么？
SDS = Simple Dynamic String，是 Redis 底层的数据结构。这里指的是在应用层模拟 Redis SDS 的思想，用**固定大小的二进制块**来存储计数器数据。

### 为什么需要？

**问题**：点赞数、收藏数等计数器，如果每次都查数据库，性能很差。

**方案**：用一个 20 字节的固定大小二进制块存储 5 个计数器：

```
┌──────────────────────────────────────────────┐
│  20 字节 SDS 二进制块                         │
│  ┌──────┬──────┬──────┬──────┬──────┐        │
│  │ 阅读 │ 点赞 │ 收藏 │ 评论 │ 转发 │        │
│  │ 4B   │ 4B   │ 4B   │ 4B   │ 4B   │        │
│  └──────┴──────┴──────┴──────┴──────┘        │
│  IDX=0   IDX=1   IDX=2   IDX=3   IDX=4       │
└──────────────────────────────────────────────┘
```

### 读取方式
```java
// 读取点赞数（第2个 int32，偏移量 4 字节）
byte[] raw = redis.get("cnt:V1:knowpost:123");
int likeCount = readInt32BE(raw, 4);  // 大端序读取
```

### 为什么要用大端序？
大端序（Big-Endian）是网络字节序，高位字节在前。这样可以用二进制比较来排序，Redis 内部也使用大端序。

### 关键代码位置
- 读取：`counter/schema/SdsUtils.java`
- 写入：`counter/service/impl/CounterServiceImpl.java`

## 5. Feed 三级缓存设计

### 是什么？
三级缓存 = **Caffeine（L1）→ Redis（L2）→ 数据库（L3）**，逐层兜底，尽量不让请求打到数据库。

### 架构图

```
用户请求
   │
   ▼
┌─────────────────────────────────┐
│  L1: Caffeine（JVM本地缓存）      │
│  特点：速度极快，但只在单机有效    │
│  TTL: 60秒                      │
│  命中率：约 80%                  │
└─────────────────────────────────┘
   │ 未命中
   ▼
┌─────────────────────────────────┐
│  L2: Redis（分布式缓存）          │
│  特点：多实例共享，但有网络开销    │
│  TTL: 60-90秒                   │
└─────────────────────────────────┘
   │ 未命中
   ▼
┌─────────────────────────────────┐
│  L3: MySQL 数据库                │
│  最后兜底                        │
└─────────────────────────────────┘
```

### 分片设计

**小时分片**：`hourSlot = System.currentTimeMillis() / 3600000L`

```
新发布的帖子 → 写入当前小时的缓存槽
               不会影响前一个小时的缓存
               避免全量失效！
```

### 热点 Key 检测（HotKeyDetector）

```
滑动窗口：60秒，分10段（每段6秒）
   │
   ▼
每段记录访问次数
   │
   ▼
计算总热度 = 所有段之和
   │
   ▼
┌─────────────────────────────────┐
│  热度等级     阈值     TTL延长   │
│  NONE       <50     +0s        │
│  LOW        ≥50     +20s       │
│  MEDIUM     ≥200    +60s       │
│  HIGH       ≥500    +120s      │
└─────────────────────────────────┘
```

### 防击穿：SingleFlight 模式

```java
// 伪代码
Object lock = map.computeIfAbsent(key, k -> new Object());
synchronized(lock) {
    // 双重检查：可能已经有其他线程加载完了
    result = getFromCache(key);
    if (result != null) return result;
    result = loadFromDB(key);
    saveToCache(key, result);
}
```

### 关键代码位置
- 缓存配置：`cache/config/CacheConfig.java`
- 热点检测：`cache/config/HotKeyDetector.java`
- Feed 服务：`knowpost/service/impl/KnowPostFeedServiceImpl.java`

## 6. Kafka 异步写+写聚合

### 是什么？
**异步写**：用户点赞后，先返回成功，再异步更新数据库计数器。
**写聚合**：把多次小操作合并成一次批量操作。

### 流程

```
用户点赞
   │
   ▼
┌─────────────────────────────────┐
│  1. Redis Bitmap 原子翻转       │
│     (Lua脚本保证原子性)         │
│  2. 发送 CounterEvent 到 Kafka  │
│  3. 立即返回成功                │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  CounterAggregationConsumer     │
│  (Kafka消费者，groupId=counter-egg)│
│  收到事件 → HINCRBY 聚合到Hash  │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  @Scheduled(fixedDelay=1000)    │
│  每秒扫描所有 agg:* key         │
│  把增量合并到 SDS 摘要层        │
└─────────────────────────────────┘
```

### 为什么这样设计？
| 操作 | 延迟 | 吞吐量 |
|------|------|--------|
| 同步写数据库 | 10-50ms | 低 |
| 异步写 Kafka | 1-5ms | 高 |
| 聚合后批量写 | 批量操作 | 更高 |

## 7. 分片位图+计数重建策略

### 是什么？

**分片位图**：把一个大的 Bitmap 拆成多个小片，每片 32768 位（4KB）。

```
用户ID: 100000
   │
   ▼
分片ID: 100000 / 32768 = 3
位偏移: 100000 % 32768 = 2464
   │
   ▼
Redis Key: bm:like:knowpost:123:3
           第32768个位置的 bit
```

### 为什么分片？
| 问题 | 单个大Bitmap | 分片Bitmap |
|------|-------------|-----------|
| 内存分配 | 一次分配1GB+ | 按需分配4KB |
| 网络传输 | 每次传输整个大Bitmap | 只传相关分片 |
| Redis阻塞 | BITCOUNT可能阻塞 | 单片计算很快 |

### 计数重建策略

**什么时候需要重建？**
- SDS 摘要层数据损坏
- SDS 大小不对（应该是20字节）
- SDS 不存在

**重建流程（带保护机制）**：

```
读取 SDS 失败
   │
   ▼
┌─────────────────────────────────┐
│  1. 获取分布式锁                │
│     lock:sds-rebuild:{etype}:{eid}│
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  2. 限流检查                    │
│     3次/10秒（防止频繁重建）     │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  3. 指数退避检查                │
│     delay = baseMs × 2^exp      │
│     最大30秒                    │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  4. 双重检查                    │
│     可能其他线程已经重建完了     │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  5. 扫描所有位图分片            │
│     BITCOUNT 统计每个用户的点赞  │
│  6. 写入 SDS 摘要层             │
└─────────────────────────────────┘
```

### 关键代码位置
- 位图分片：`counter/schema/BitmapShard.java`
- 重建逻辑：`counter/service/impl/CounterServiceImpl.java`

## 8. 缓存三剑客预防策略

### 是什么？
缓存三剑客 = **缓存穿透、缓存击穿、缓存雪崩**

### 1. 缓存穿透（查询不存在的数据）

```
问题：恶意请求查询 ID=-1 的帖子
      数据库也没有，每次都会打到数据库

解决方案：
┌─────────────────────────────────┐
│  布隆过滤器 / 空值缓存          │
│  查询不存在的数据 → 缓存空值     │
│  TTL 设置短一些（如 60秒）       │
└─────────────────────────────────┘
```

### 2. 缓存击穿（热点 Key 过期）

```
问题：热帖缓存过期，瞬间大量请求打到数据库

解决方案：
┌─────────────────────────────────┐
│  SingleFlight + 热点Key检测     │
│  1. SingleFlight 保证只放一个请求│
│  2. 热点Key自动延长TTL          │
│  3. 双重检查防止重复加载         │
└─────────────────────────────────┘
```

### 3. 缓存雪崩（大量 Key 同时过期）

```
问题：一批缓存同时过期，数据库压力骤增

解决方案：
┌─────────────────────────────────┐
│  1. TTL 加随机值                │
│     60s + random(0, 30)s        │
│  2. 小时分片                    │
│     新旧数据分开放，不会同时失效  │
│  3. 多级缓存                    │
│     L1 过期了，L2 还能顶一下     │
└─────────────────────────────────┘
```

### 关键代码位置
- SingleFlight：`knowpost/service/impl/KnowPostFeedServiceImpl.java`
- 热点检测：`cache/config/HotKeyDetector.java`

## 9. Java 版本新特性

### 本项目使用 Java 17，主要用到的新特性：

### 1. 文本块（Text Blocks）- Java 13+
```java
// 旧写法

// 新写法（三个引号）

    {
```

### 2. Switch 表达式 - Java 14+
```java
// 旧写法
String result;
switch (status) {
    case "DRAFT":
        result = "草稿";
        break;
    case "PUBLISHED":
        result = "已发布";
        break;
    default:

    case "DRAFT" -> "草稿";

    default -> "未知";

```

### 3. Record 类 - Java 14+
```java
// 旧写法：需要写 getter、equals、hashCode、toString
public class TokenPair {
    private final String accessToken;
    private final String refreshToken;
    // 构造函数、getter、equals、hashCode...

// 新写法：一行搞定
public record TokenPair(
    String accessToken,
    Instant accessTokenExpiresAt,
    String refreshToken,
    Instant refreshTokenExpiresAt,
    String refreshTokenId

```

### 4. sealed 类 - Java 17
```java

public final class Triangle extends Shape {}
```

### 5. Pattern Matching for instanceof - Java 16+
```java
// 旧写法
if (obj instanceof String) {
    String s = (String) obj;
    // 使用 s
}

// 新写法
if (obj instanceof String s) {
    // 直接使用 s
}
```

## 10. 雪花 ID 生成器（Snowflake）

### 是什么？
Snowflake 是 Twitter 开源的分布式 ID 生成算法，生成 64 位整数 ID。

### ID 结构（64位）

```
┌────────────────────────────────────────────────────────────────────┐
│ 0 │ 00000000 00000000 00000000 00000000 00000000 0 │ 00000 │ 00000 │ 000000000000 │
│符号│                41位时间戳                       │5位数据中心│5位工作机器│  12位序列号  │
│位  │            毫秒级，约69年                       │    ID    │    ID    │   同毫秒内   │
└────────────────────────────────────────────────────────────────────┘
```

### 为什么用雪花 ID？

| 对比项 | 自增 ID | UUID | 雪花 ID |
|--------|---------|------|---------|
| 全局唯一 | 单机唯一 | 全局唯一 | 全局唯一 |
| 有序性 | 有序 | 无序 | 趋势递增 |
| 长度 | 4-8字节 | 16字节 | 8字节 |
| 索引友好 | ✓ | ✗ | ✓ |
| 分布式 | 需要协调 | 天然支持 | 天然支持 |

## 11. 深分页解决方案

### 问题是什么？

```sql
-- 第1页（快）
SELECT * FROM know_posts ORDER BY publish_time DESC LIMIT 20 OFFSET 0;

-- 第1000页（慢）
SELECT * FROM know_posts ORDER BY publish_time DESC LIMIT 20 OFFSET 19980;
```

**原因**：OFFSET 越大，MySQL 需要扫描的行越多，即使只需要20行。

### 解决方案：游标分页（Cursor-based Pagination）

```
第1页请求：
GET /api/v1/knowposts/feed?page=1&size=20

返回：
{
  "items": [...],
  "cursor": "MTcyMzQ1Njc4OQ=="  // 最后一条的 publish_time 编码
}

第2页请求：
GET /api/v1/knowposts/feed?cursor=MTcyMzQ1Njc4OQ==&size=20
```

**原理**：用上一页的最后一条记录作为"游标"，直接从那个位置开始取数据，不需要 OFFSET。

```sql
-- 游标分页
SELECT * FROM know_posts 
WHERE publish_time < '2024-01-15 10:30:00'  -- 游标值
ORDER BY publish_time DESC 
LIMIT 20;
```

### 对比

| 方案 | OFFSET分页 | 游标分页 |
|------|-----------|---------|
| 深分页性能 | 越翻越慢 | 恒定速度 |
| 跳页 | 支持 | 不支持 |
| 实现复杂度 | 简单 | 中等 |
| 适用场景 | 后台管理 | 信息流、Feed流 |

### 关键代码位置
- Mapper SQL：`knowpost/mapper/KnowPostsMapper.java`

## 12. RAG 知识问答系统

### 是什么？
RAG = Retrieval-Augmented Generation，检索增强生成。

```
用户提问
   │
   ▼
┌─────────────────────────────────┐
│  1. 检索阶段（Retrieval）        │
│  把问题转成向量 → 查找相似文档   │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  2. 增强阶段（Augmented）        │
│  把检索到的文档作为上下文        │
│  和用户问题一起喂给 LLM          │
└─────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────┐
│  3. 生成阶段（Generation）       │
│  LLM 基于上下文生成回答          │
└─────────────────────────────────┘
```

### 为什么需要 RAG？

**问题**：LLM 的训练数据有截止日期，不知道最新的知识。

**解决**：先从知识库检索相关文档，再让 LLM 基于这些文档回答。

### 本项目的实现

```
帖子发布 → 向量化 → 存入 Elasticsearch
用户提问 → 向量化 → Elasticsearch 向量搜索
                     │
                     ▼
              返回 Top-K 相似文档
                     │
                     ▼
              拼接 Prompt：问题 + 文档
                     │
                     ▼
              DeepSeek 生成回答
```

### 关键代码位置
- 向量存储：`cache/config/ElasticsearchConfig.java`
- RAG 集成：`knowpost/service/impl/KnowPostServiceImpl.java`

## 13. Kafka 灾难回放

### 是什么？
灾难回放 = **Kafka 消费失败后，可以从头重新消费**，确保数据不丢失。

### 为什么需要？

**场景**：
1. 消费者处理逻辑有 Bug，导致数据不一致
2. 下游服务宕机，消息丢失
3. 需要重建缓存/计数器

### 实现方式

```
正常消费（从 latest offset 开始）
   │
   ▼
发现数据不一致！
   │
   ▼
┌─────────────────────────────────┐
│  CounterRebuildConsumer         │
│  (默认禁用，counter.rebuild.enabled=true)│
│  从 earliest offset 重新消费    │
│  直接折叠每个事件到 SDS         │
└─────────────────────────────────┘
```

### 关键代码位置
- 灾难回放消费者：`counter/event/CounterRebuildConsumer.java`
