## 第二部分：参考答案详解

---

### 问题 1

**参考答案：**

**Bitmap 优势**：
1. **节省内存**：每个用户只占1个bit，1亿用户仅需约12MB
2. **位运算高效**：支持 BITCOUNT、BITOP 等聚合操作
3. **查询速度快**：O(1) 复杂度判断某用户是否点赞

**Bitmap 劣势**：
1. **位偏移限制**：需要预先规划位数（如 userId % 10000000）
2. **稀疏问题**：如果大量 userId 很小会浪费前面的大量位
3. **无法存储用户信息**：只能存0/1，无法存用户名等额外信息

**Set 优势**：可以存储完整用户信息，天然支持遍历
**Set 劣势**：每个用户占约100字节，1亿用户需10GB+

项目选择 Bitmap 主要考虑点赞是简单的0/1判断，且用户量可能很大。

---

### 问题 2

**参考答案：**

**需要 Lua 脚本的原因**：

1. **读-改-写不是原子操作**：普通 INCR 看似原子，但项目中需要"检查是否已点赞"+"更新计数"两步
2. **检查+更新需要原子性**：如果先检查 hasLiked=0，再 increment，中间可能有并发请求导致重复点赞
3. **Lua 脚本在 Redis 中原子执行**：
```lua
local current = redis.call('GETBIT', key, pos)
if current == 0 then
    redis.call('SETBIT', key, pos, 1)
    redis.call('INCR', counterKey)
end
```

直接用 INCR 的问题：无法判断用户是否已点赞，可能导致重复计数。

---

### 问题 3

**参考答案：**

**位映射公式**：`pos = userId % 10000000`

**优点**：
1. 均匀分布：userId 取模后分散到 0-9999999 范围
2. 固定大小：1000万个位 ≈ 1.25MB，固定内存占用
3. 简单计算：取模运算速度快

**缺点**：
1. 碰撞：不同的 userId 可能映射到同一位（如 userId=1 和 userId=10000001）
2. 扩容困难：一旦确定模数，很难修改

**解决方案**：实际项目中还会额外存储一个 Set `counter:like:users:{postId}` 存储真实点赞用户列表，用于精确判断。Bitmap 只做计数。

---

### 问题 4

**参考答案：**

**缓存击穿问题**：当一个热点 key 过期瞬间，大量并发请求同时发现缓存失效，全部涌入数据库查询，可能导致数据库崩溃。

**SingleFlight 模式**：
```java
Object lock = singleFlight.computeIfAbsent(pageKey, k -> new Object());
synchronized (lock) {
    // 双重检查缓存
    String cached = redis.get(pageKey);
    if (cached != null) {
        return deserialize(cached);
    }
    // 只有第一个请求查数据库，其他等待
    return queryFromDB();
}
```

原理：多个并发请求同一个 key 时，只有第一个请求去查数据库，其他请求等待第一个请求的结果（类似 Go 的 singleflight）。

### 问题 5

**参考答案：**

**三级缓存架构**：

| 层级 | 存储 | TTL | 作用 |
|------|------|-----|------|
| L1 Caffeine | 本地内存 | 5-30分钟 | 最高频访问，本地无网络开销 |
| L2 Redis | 分布式内存 | 30分钟-2小时 | 跨服务共享，减少远程调用 |
| L3 DB | 磁盘 | 持久化 | 数据最终来源 |

**淘汰策略**：
- Caffeine：LRU + 最大条目数限制
- Redis：LRU + TTL 过期
- DB：无淘汰，需要应用层保证数据一致性

访问顺序：L1 → L2 → L3，写入顺序相反：L3 → L2 → L1

---

### 问题 6

**参考答案：**

**缓存双删原因**：

1. **第一次删除**：事务提交前，删除可能存在的旧缓存
2. **延迟删除**：事务提交后，延迟几百毫秒再删除一次

**目的**：防止在删除缓存后、事务提交前，有另一个请求读取了数据库的旧数据并写入缓存，导致缓存数据比数据库还旧。

**时机**：
```java
// 第一次删除（事务内，DB更新前）
redis.delete(cacheKey);

// DB 更新
mapper.update(post);

// 事务提交后
delay(() -> redis.delete(cacheKey)); // 延迟删除
```

### 问题 7

**参考答案：**

**热键判定**：
```java
private static final int HOT_THRESHOLD = 1000; // 1000次/分钟

public boolean isHotKey(long postId) {
    String key = "hot:post:" + postId;
    String count = redis.get(key);
    return count != null && Long.parseLong(count) >= HOT_THRESHOLD;
}
```

**热键处理**：
1. **延长 TTL**：热键缓存延长过期时间，减少淘汰
2. **预加载**：可以提前将热点数据加载到 L1 缓存
3. **限流熔断**：极端情况下可以触发限流保护

### 问题 8

**参考答案：**

**事务内操作顺序**：
```java
@Transactional
public void follow(long followerId, long targetId) {
    // 1. 业务校验（可不在事务内）
    
    // 2. 写入关注关系
    followingMapper.insert(followerId, targetId);
    
    // 3. 更新计数（在事务内，保证一致性）
    counterService.incrementFollowing(followerId, 1);
    counterService.incrementFollowers(targetId, 1);
    
    // 4. 写入 Outbox（在事务内，与业务数据同一事务）
    outboxMapper.insert(...);
}
```

**Outbox 必须在事务内的原因**：保证"业务数据"和"消息"的原子性。要么都成功，要么都回滚。避免出现"业务成功但消息未发送"的情况。

### 问题 9

**参考答案：**

**从 DB 查询方案**：
- 优点：数据准确，支持分页和排序，可查询完整用户信息
- 缺点：每次查询都要 DB，延迟较高

**从 Bitmap 查询方案**：
- 优点：内存操作，极快
- 缺点：Bitmap 只支持位运算，不支持分页和排序

**项目选择 DB 的原因**：
1. 关注列表需要分页展示（每页20人）
2. 需要展示用户详细信息（昵称、头像）
3. 关注量通常不大，DB 查询可接受

如果需要展示"粉丝中谁关注了我"，则需要 Bitmap 做集合运算（BITOP AND）。

### 问题 10

**参考答案：**

**异步传播优势**：
1. **解耦**：关注服务和搜索服务、通知服务解耦
2. **削峰**：高并发时消息积压， 소비者按能力消费
3. **性能**：主流程不等待下游处理完成

**潜在问题**：
1. **最终一致性**：存在延迟，可能出现"我关注了但搜索搜不到"
2. **消息丢失**：需要保证消息不丢（Kafka 可靠性配置）
3. **顺序性**：需要保证同一用户的操作顺序（分区策略）

**项目设计**：通过 Canal 监听 binlog → Kafka → 消费者处理，保证数据最终一致。

### 问题 11

**参考答案：**

```java
public boolean hasLiked(long userId, long postId) {
    String key = "counter:like:" + postId;
    long pos = userId % 10000000;
    return redis.opsForValue().getBit(key, pos) == 1;
}
```

**原理**：使用 Redis 的 GETBIT 命令获取指定位置的 bit 值
- 返回 1：用户已点赞
- 返回 0：用户未点赞

注意：这里存在前面提到的碰撞问题，所以项目中可能还维护了一个 Set 来精确记录点赞用户列表。

### 问题 12

**参考答案：**

**自愈机制触发条件**：
1. **定时任务**：每分钟检查计数与 Bitmap 位的总和是否一致
2. **主动纠正**：发现不一致时重新遍历 Set 重建 Bitmap

```java
public void selfHeal(long postId) {
    Set<Long> likedUsers = getLikedUserSet(postId);
    String bitmapKey = "counter:like:" + postId;
    
    // 重新设置所有位
    for (Long userId : likedUsers) {
        redis.opsForValue().setBit(bitmapKey, userId % 10000000, 1);
    }
}
```

**Bitmap 不一致原因**：
1. 初始设计缺陷导致的碰撞
2. Redis 持久化失败
3. 运维操作导致数据丢失

### 问题 13

**参考答案：**

**幂等性问题**：如果不做处理，用户多次点击"关注"会导致：
1. 关注计数重复+1
2. 重复写入关注关系（数据库唯一约束会报错）
3. 重复发送通知

**代码处理**：
```java
// 先检查是否已关注
if (exists(followerId, targetId)) {
    throw new BusinessException(ErrorCode.BAD_REQUEST, "已关注");
}
// 再插入
followingMapper.insert(followerId, targetId);
```

但这仍有并发问题，更好的方式是使用数据库唯一约束 + 异常捕获：
```java
try {
    followingMapper.insert(followerId, targetId);
} catch (DuplicateKeyException e) {
    // 已存在，忽略
}
```

### 问题 14

**参考答案：**

**乐观更新优点**：
1. 响应快：用户点击立即看到变化，无需等待服务器响应
2. 减少服务器压力
3. 用户体验好

**乐观更新缺点**：
1. **数据不一致**：服务器返回失败时需要回滚
2. **竞态条件**：多次快速点击可能导致重复请求

**项目处理**：
```typescript
const handleClick = async () => {
    setLoading(true); // 禁用按钮，防止重复点击
    try {
        await apiCall();
    } catch {
        // 失败回滚本地状态
        setFollowing(!following);
    } finally {
        setLoading(false);
    }
};
```
