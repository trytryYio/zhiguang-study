## 一、核心逻辑总览

### 个人资料模块做了什么？

用户登录后，可以修改自己的昵称、简介、性别、生日、知光号、学校、标签，以及上传头像。

### 两个接口

| 接口 | 方法 | 用途 |
|------|------|------|
| `/api/v1/profile` | PATCH | 部分更新个人资料（可选字段） |
| `/api/v1/profile/avatar` | POST | 上传头像图片到阿里云 OSS 并更新用户头像 URL |

### 核心流程图

```
PATCH /api/v1/profile
    Body: { nickname: "...", bio: "...", zgId: "..." }（可选字段）
    ↓
[1] ProfileController.patch()
    ├─ 从 JWT 提取 userId（防越权）
    └─ ProfileService.updateProfile(userId, request)
        ↓
        ① 查用户存在
        ② 校验至少提交一个字段
        ③ 知光号唯一性校验
        ④ 构建 patch 对象
        ⑤ 写入 MySQL
        ⑥ 回读最新快照返回


POST /api/v1/profile/avatar
    Body: multipart/form-data, file=头像图片
    ↓
[2] ProfileController.uploadAvatar()
    ├─ 从 JWT 提取 userId
    ├─ OssStorageService.uploadAvatar(userId, file) → 上传到阿里云 OSS → 返回 URL
    └─ ProfileService.updateAvatar(userId, url)
        ├─ 查用户存在
        ├─ 仅更新 avatar 字段
        └─ 回读最新快照返回
```

**流程图只负责让你先看到全貌。**
**下面正式教学时，按 ①②③ 顺序讲。**
**某个方法 / 类第一次出现，就立刻讲透。**
**不跳过嵌套调用，不让你知识断层。**

## 三、按执行流程学习（方法级别详解）

### 流程 1：资料更新 PATCH /api/v1/profile

---

#### 第 0 步：先看入口请求长什么样

资料更新接口接收的请求体来自 `ProfilePatchRequest`。

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/api/dto/ProfilePatchRequest.java`

```java
public record ProfilePatchRequest(
        @Size(min = 1, max = 64, message = "昵称长度需在 1-64 之间") String nickname,
        @Size(max = 512, message = "个人描述长度不能超过 512") String bio,
        @Pattern(regexp = "(?i)MALE|FEMALE|OTHER|UNKNOWN", message = "性别取值为 MALE/FEMALE/OTHER/UNKNOWN") String gender,
        @PastOrPresent(message = "生日不能晚于今天") LocalDate birthday,
        @Pattern(regexp = "^[a-zA-Z0-9_]{4,32}$", message = "知光号仅支持字母、数字、下划线，长度 4-32") String zgId,
        @Size(max = 128, message = "学校名称长度不能超过 128") String school,
        String tagJson
){ }
```

**这里的 7 个字段你要抓 3 个重点：**

1. **所有字段都是可选的**
   没有 `@NotBlank` 或 `@NotNull`。因为 PATCH 是部分更新，用户可能只改昵称，或者只改生日。不提交的字段是 `null`，后面 Service 层会判断"只更新非 null 字段"。

2. **每个字段有自己的校验规则**
   - `nickname`：长度 1-64
   - `bio`：最长 512
   - `gender`：只能是 `MALE`/`FEMALE`/`OTHER`/`UNKNOWN`（`(?i)` 表示大小写不敏感）
   - `birthday`：不能晚于今天
   - `zgId`：字母+数字+下划线，4-32 位
   - `school`：最长 128
   - `tagJson`：没有校验，直接透传 JSON 字符串

3. **`record` 是 Java 的数据载体**
   专门用来装请求参数，配合 Controller 上的 `@Valid` 使用，Spring 会先自动校验。比如用户传了 `gender: "INVALID"`，直接 400，不进业务逻辑。

## 第一部分：先把 Controller 入口讲透

### [1] ProfileController.patch()

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/api/ProfileController.java:47-53`

```java
@PatchMapping
public ProfileResponse patch(@AuthenticationPrincipal Jwt jwt,
                             @Valid @RequestBody ProfilePatchRequest request) {
    long userId = jwtService.extractUserId(jwt);
    return profileService.updateProfile(userId, request);
}
```

### 这个方法只做 3 件事

#### 1. 接住 PATCH 请求

`@PatchMapping` 意思是：
- 路径是 `/api/v1/profile`（类上的 `@RequestMapping` 定了前缀）
- HTTP 方法必须是 `PATCH`
- 这是资料更新接口入口

为什么用 PATCH 而不是 PUT？
因为 PATCH 是**部分更新** —— 用户只提交想改的字段，不提交的保持不动。PUT 是全量替换。

#### 2. 接住两个参数

- `@AuthenticationPrincipal Jwt jwt`：Spring Security 自动注入的已验证 JWT
- `@Valid @RequestBody ProfilePatchRequest request`：请求体 + 自动字段校验

#### 3. 从 JWT 拿 userId，不是前端传

```java
long userId = jwtService.extractUserId(jwt);
```

**为什么不用前端传 userId？**
因为防越权。如果前端传 `"userId": 123`，恶意用户可以改成 `"userId": 456` 去改别人的资料。
从 JWT 里取，就只能改自己的。

这里 `jwtService.extractUserId()` 是第一次出现，所以继续讲。

---

### [2] JwtService.extractUserId()

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/token/JwtService.java:122-131`

```java
public long extractUserId(Jwt jwt) {
    Object claim = jwt.getClaims().get(CLAIM_USER_ID);
    if (claim instanceof Number number) {
        return number.longValue();
    }
    if (claim instanceof String text) {
        return Long.parseLong(text);
    }
    throw new IllegalArgumentException("Invalid user id in token");
}
```

### 这段代码按 3 步理解

#### 1. 从 JWT claims 里取 `uid` 字段

```java
Object claim = jwt.getClaims().get(CLAIM_USER_ID);
```

`CLAIM_USER_ID` 是 `"uid"`，这是在签发 Access Token 时写进去的自定义 claim。

#### 2. 类型兼容处理

JWT claims 的类型取决于序列化方式：
- 如果是 `Number`（直接存 long），转成 `longValue()`
- 如果是 `String`（序列化后传输），`Long.parseLong()` 转回来

#### 3. 如果都不是，抛异常

说明 token 里根本没这个 claim，或者类型完全不对。
这通常意味着 token 不是本系统签发的。

---

### [3] 委托给业务层

```java
return profileService.updateProfile(userId, request);
```

这一行把业务逻辑完全交给 `ProfileService`。
Controller 层只做"收请求 → 提取身份 → 委托 → 返回"。

### 到这里，Controller 入口你应该形成完整理解：
1. 收 PATCH 请求
2. Spring 自动校验 `ProfilePatchRequest` 字段格式
3. 从 JWT 提取 userId（防越权）
4. 委托给 `ProfileService.updateProfile()`

现在才能进入真正的核心：`ProfileServiceImpl.updateProfile()`。

## 第二部分：正式拆 ProfileServiceImpl.updateProfile()

### [4] ProfileServiceImpl.updateProfile() 总体代码

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/service/impl/ProfileServiceImpl.java:65-101`

```java
@Override
@Transactional
public ProfileResponse updateProfile(long userId, ProfilePatchRequest req) {
    // 读取当前用户，作为更新与唯一性校验的基准
    User current = userMapper.findById(userId);

    if (current == null) {
        throw new BusinessException(ErrorCode.IDENTIFIER_NOT_FOUND, "用户不存在");
    }

    // 至少要提交一个字段，否则属于无效请求
    boolean hasAnyField = req.nickname() != null || req.bio() != null || req.gender() != null
            || req.birthday() != null || req.zgId() != null || req.school() != null
            || req.tagJson() != null;

    if (!hasAnyField) {
        throw new BusinessException(ErrorCode.BAD_REQUEST, "未提交任何更新字段");
    }

    // 知光号唯一性校验：仅在提交且非空时检查（排除自己）
    if (req.zgId() != null && !req.zgId().isBlank()) {
        boolean exists = userMapper.existsByZgIdExceptId(req.zgId(), current.getId());

        if (exists) {
            throw new BusinessException(ErrorCode.ZGID_EXISTS);
        }
    }

    // 仅写入非空字段，避免把未提交字段覆盖成 null
    User patch = getUser(req, current);
    userMapper.updateProfile(patch);

    // 更新后回读，保证返回数据为最新快照
    User updated = userMapper.findById(userId);

    return toResponse(updated);
}
```

这一个方法看起来不长，但里面嵌套了很多第一次出现的方法。
所以我们必须按顺序拆。

### [5] 第 ① 步：查用户存在

```java
User current = userMapper.findById(userId);

if (current == null) {
    throw new BusinessException(ErrorCode.IDENTIFIER_NOT_FOUND, "用户不存在");
}
```

### 为什么第一步先查用户？

因为更新的前提是这个人存在。
如果 userId 是伪造的或者用户被删了，就没必要继续。

这里用 `userMapper.findById()` 直接查，而不是走 `UserService`。

**为什么 ProfileServiceImpl 可以直接用 UserMapper？**
因为资料更新是简单的单表操作，不需要经过 `UserService` 的业务封装。
`UserService` 更多是给 `AuthService` 这种跨模块调用用的。

`UserMapper.findById()` 是 MyBatis Mapper 接口方法：

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/user/mapper/UserMapper.java:21`

```java
User findById(@Param("id") Long id);
```

对应一条 `SELECT * FROM users WHERE id = ?` 的 SQL。

这里又第一次出现了 `User` 实体，所以也要讲。

### [6] User 实体长什么样？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/user/domain/User.java`

```java
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class User {
    private Long id;
    private String phone;
    private String email;
    private String passwordHash;
    private String nickname;
    private String avatar;
    private String bio;
    private String zgId;
    private String gender;
    private LocalDate birthday;
    private String school;
    private String tagsJson;
    private Instant createdAt;
    private Instant updatedAt;
}
```

### 这里你要抓 2 个重点

#### 1. `@Data` + `@Builder` + `@NoArgsConstructor` + `@AllArgsConstructor`

这是 Lombok 的四件套：
- `@Data`：自动生成所有 getter/setter、`equals()`、`hashCode()`、`toString()`
- `@Builder`：支持 `User.builder().id(1).nickname("xxx").build()` 的链式构建
- `@NoArgsConstructor`：无参构造（MyBatis 需要）
- `@AllArgsConstructor`：全参构造（Builder 底层需要）

#### 2. 数据库实体 vs DTO 的区别

`User` 是数据库表的完整映射，包含所有字段（包括敏感的 `passwordHash`）。
而 `ProfileResponse` 是对外 DTO，只包含可以公开的字段。
这就是为什么后面需要 `toResponse()` 做转换——不能直接把 `User` 扔给前端。

所以这一步你应该形成这样的认识：
> `User` 是数据库里的完整用户记录，`ProfileResponse` 是给前端看的过滤后的快照。

---

### [7] 第 ② 步：校验至少提交一个字段

```java
boolean hasAnyField = req.nickname() != null || req.bio() != null || req.gender() != null
        || req.birthday() != null || req.zgId() != null || req.school() != null
        || req.tagJson() != null;

if (!hasAnyField) {
    throw new BusinessException(ErrorCode.BAD_REQUEST, "未提交任何更新字段");
}
```

### 为什么需要这层校验？

因为 `ProfilePatchRequest` 里所有字段都没有 `@NotBlank`。
用户可以传一个空 JSON `{}` 过来。
如果不检查，后面的 `getUser()` 会构建一个没有任何字段更新的 patch 对象，白白执行一次无意义的数据库 UPDATE。

所以这一步是"守门员"：
- 至少有一个字段不是 `null`，才继续
- 全 `null`，直接 400 拒绝

这里又出现了 `BusinessException` 和 `ErrorCode`，和认证模块里的一样，不再赘述。

### [8] 第 ③ 步：知光号唯一性校验

```java
if (req.zgId() != null && !req.zgId().isBlank()) {
    boolean exists = userMapper.existsByZgIdExceptId(req.zgId(), current.getId());

    if (exists) {
        throw new BusinessException(ErrorCode.ZGID_EXISTS);
    }
}
```

### 为什么要单独校验 zgId？

因为知光号是用户的唯一标识（类似 Twitter 的 @handle）。
不能两个人用同一个 zgId。

`existsByZgIdExceptId` 的意思是：
> 查有没有**其他人**（excludeId 除外）已经用了这个 zgId。

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/user/mapper/UserMapper.java:27`

```java
boolean existsByZgIdExceptId(@Param("zgId") String zgId, @Param("excludeId") Long excludeId);
```

对应 SQL 类似：
```sql
SELECT EXISTS(SELECT 1 FROM users WHERE zg_id = ? AND id != ?)
```

### 这里有 2 个关键设计

#### 1. 为什么排除自己？

因为用户可能只是改了昵称但没改 zgId。
如果不排除自己，用户每次更新资料都会报"知光号已存在"。

#### 2. 为什么先判断 `!req.zgId().isBlank()`？

因为用户可能提交了一个空字符串 `""` 来清空 zgId。
空字符串不需要做唯一性校验。

### [10] ProfileServiceImpl.getUser() — 为什么不是直接用 request？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/service/impl/ProfileServiceImpl.java:108-133`

```java
private static User getUser(ProfilePatchRequest req, User current) {
    User patch = new User();
    patch.setId(current.getId());
    if (req.nickname() != null) {
        patch.setNickname(req.nickname().trim());
    }
    if (req.bio() != null) {
        patch.setBio(req.bio().trim());
    }
    if (req.gender() != null) {
        patch.setGender(req.gender().trim().toUpperCase());
    }
    if (req.birthday() != null) {
        patch.setBirthday(req.birthday());
    }
    if (req.zgId() != null) {
        patch.setZgId(req.zgId().trim());
    }
    if (req.school() != null) {
        patch.setSchool(req.school().trim());
    }
    if (req.tagJson() != null) {
        patch.setTagsJson(req.tagJson());
    }
    return patch;
}
```

### 这个方法为什么需要存在？

因为 `ProfilePatchRequest` 是 DTO，`User` 是数据库实体。
不能直接把 DTO 塞给 MyBatis 去更新。

### 这个方法做了 4 件重要的事

#### 1. 只设置非 null 字段

```java
if (req.nickname() != null) { ... }
```

如果用户只改了昵称，patch 对象就只有 `id` 和 `nickname` 有值。
其他字段全是默认 `null`。

后面 MyBatis 的 `updateProfile` 应该是动态 SQL：
```xml
<update id="updateProfile">
    UPDATE users
    <set>
        <if test="nickname != null">nickname = #{nickname},</if>
        <if test="bio != null">bio = #{bio},</if>
        ...
    </set>
    WHERE id = #{id}
</update>
```

只有非 null 的字段才会出现在 SET 子句里。
这样就不会把没提交的字段覆盖成 `null`。

#### 2. 字符串统一 trim 去空格

```java
patch.setNickname(req.nickname().trim());
```

用户输入 `"  MyNickname  "` → 存成 `"MyNickname"`。
避免前后空格导致数据脏乱。

#### 3. gender 统一转大写

```java
patch.setGender(req.gender().trim().toUpperCase());
```

用户传 `"male"` → 存成 `"MALE"`。
这样数据库里性别值是统一的，后面查询/统计不会出岔子。

#### 4. 方法是 `static`

```java
private static User getUser(...)
```

因为它不依赖任何实例成员，纯数据转换。
static 方法调用不需要 `this`，更高效。

### 到这里，patch 对象构建你应该形成完整理解：
1. 新建一个 User 对象
2. 只设置用户提交的字段
3. 字符串字段做 trim 标准化
4. gender 转大写
5. 返回给 Mapper 做动态更新

现在才能进入第 ⑤ 步：写数据库。

### [12] 第 ⑥ 步：回读最新快照

```java
User updated = userMapper.findById(userId);
return toResponse(updated);
```

### 为什么更新后还要再查一次？

因为：
1. MyBatis 的 `updateProfile` 不会回填更新后的完整实体
2. 数据库可能有触发器/默认值/时间戳自动更新（比如 `updated_at`）
3. 保证返回给前端的数据 100% 是数据库里最新状态

这一步叫"**写后回读**"（read-after-write），是保证数据一致性的常见做法。

## 第二部分：头像上传接口 POST /api/v1/profile/avatar

### [14] ProfileController.uploadAvatar()

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/api/ProfileController.java:64-71`

```java
@PostMapping("/avatar")
public ProfileResponse uploadAvatar(@AuthenticationPrincipal Jwt jwt,
                                    @RequestPart("file") MultipartFile file) {
    long userId = jwtService.extractUserId(jwt);
    String url = ossStorageService.uploadAvatar(userId, file);
    return profileService.updateAvatar(userId, url);
}
```

### 这个方法只做 4 件事

#### 1. 接收 multipart 文件上传

`@RequestPart("file") MultipartFile file` 意思是：
- HTTP 请求必须是 `multipart/form-data`
- 文件字段名叫 `file`
- Spring 会把它封装成 `MultipartFile` 对象

#### 2. 从 JWT 提取 userId

和资料更新一样，身份从 token 里取，防越权。

#### 3. 先上传到阿里云 OSS

```java
String url = ossStorageService.uploadAvatar(userId, file);
```

这一步是真正干活的地方。头像文件不是存在本地，而是上传到阿里云对象存储。
上传成功后 OSS 返回一个可访问的 URL。

这个方法是第一次出现，所以必须讲透。

### [15] OssStorageService.uploadAvatar() — 文件怎么上传到 OSS？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/storage/OssStorageService.java:26-48`

```java
public String uploadAvatar(long userId, MultipartFile file) {
    ensureConfigured();

    String original = file.getOriginalFilename();
    String ext = "";
    if (original != null && original.contains(".")) {
        ext = original.substring(original.lastIndexOf('.'));
    }
    String objectKey = props.getFolder() + "/" + userId + "-" + Instant.now().toEpochMilli() + ext;

    OSS client = new OSSClientBuilder().build(props.getEndpoint(), props.getAccessKeyId(), props.getAccessKeySecret());

    try {
        PutObjectRequest request = new PutObjectRequest(props.getBucket(), objectKey, file.getInputStream());
        client.putObject(request);
    } catch (IOException e) {
        throw new BusinessException(ErrorCode.BAD_REQUEST, "头像文件读取失败");
    } finally {
        client.shutdown();
    }

    return publicUrl(objectKey);
}
```

### 这段代码按 6 步理解

#### 1. 先检查 OSS 配置是否完整

```java
ensureConfigured();
```

如果 endpoint、accessKeyId、accessKeySecret、bucket 有一个没配，直接报错。
这叫"快速失败"——不要等到真正要上传时才因为配置缺失崩溃。

#### 2. 提取文件扩展名

```java
String original = file.getOriginalFilename();
String ext = "";
if (original != null && original.contains(".")) {
    ext = original.substring(original.lastIndexOf('.'));
}
```

用户上传 `avatar.png` → `ext = ".png"`
用户上传 `photo`（无后缀）→ `ext = ""`

保留扩展名是为了 OSS 上的文件能正确识别 MIME 类型。

#### 3. 拼接 OSS 对象键

```java
String objectKey = props.getFolder() + "/" + userId + "-" + Instant.now().toEpochMilli() + ext;
```

例如：
```
avatars/123-1713369600000.png
```

这里用 `userId + 时间戳毫秒` 做文件名，目的是：
- 保证唯一性（同一用户同一毫秒上传概率极低）
- 方便排查（从文件名就能看出是谁什么时候上传的）

#### 4. 创建 OSS 客户端并上传

```java
OSS client = new OSSClientBuilder().build(props.getEndpoint(), props.getAccessKeyId(), props.getAccessKeySecret());
PutObjectRequest request = new PutObjectRequest(props.getBucket(), objectKey, file.getInputStream());
client.putObject(request);
```

这里**每次上传都新建客户端**，上传完后 `client.shutdown()` 关闭。
简单直接，但如果上传量大，可以考虑复用客户端连接池。

#### 5. finally 里关闭客户端

```java
finally {
    client.shutdown();
}
```

不管成功还是失败，都要释放连接资源。
这是标准的 try-finally 资源管理模式。

#### 6. 返回可访问的 URL

```java
return publicUrl(objectKey);
```

### [16] OssStorageService.publicUrl() — 怎么拼出访问 URL？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/storage/OssStorageService.java:50-55`

```java
private String publicUrl(String objectKey) {
    if (props.getPublicDomain() != null && !props.getPublicDomain().isBlank()) {
        return props.getPublicDomain().replaceAll("/$", "") + "/" + objectKey;
    }
    return "https://" + props.getBucket() + "." + props.getEndpoint() + "/" + objectKey;
}
```

### 这里有 2 种 URL 拼接方式

#### 1. 有自定义域名

如果配了 `publicDomain`（比如 `https://cdn.zhiguang.cn`）：
```
https://cdn.zhiguang.cn/avatars/123-1713369600000.png
```

`replaceAll("/$", "")` 是去掉域名末尾的斜杠，避免拼接出双斜杠。

#### 2. 没有自定义域名，用 OSS 默认格式

```
https://zhiguang-bucket.oss-cn-shanghai.aliyuncs.com/avatars/123-1713369600000.png
```

### 到这里，头像上传的 OSS 部分你应该形成完整理解：
1. 检查配置
2. 取文件扩展名
3. 拼唯一对象键
4. 上传到 OSS
5. 关闭连接
6. 返回可访问 URL

现在回到 Controller，继续走第 4 步。

### [17] ProfileServiceImpl.updateAvatar() — 把 URL 写回用户资料

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/profile/service/impl/ProfileServiceImpl.java:144-161`

```java
@Override
@Transactional
public ProfileResponse updateAvatar(long userId, String avatarUrl) {
    User current = userMapper.findById(userId);
    if (current == null) {
        throw new BusinessException(ErrorCode.IDENTIFIER_NOT_FOUND, "用户不存在");
    }

    // 仅更新头像字段
    User patch = new User();
    patch.setId(userId);
    patch.setAvatar(avatarUrl);
    userMapper.updateProfile(patch);

    // 更新后回读，保证返回最新头像地址
    User updated = userMapper.findById(userId);
    return toResponse(updated);
}
```

### 这个方法比 updateProfile() 简单很多

因为：
- 不用校验"至少一个字段"（avatarUrl 就是那个字段）
- 不用校验唯一性（头像 URL 不需要唯一）
- 不用构建复杂的 patch 对象（只有 2 个字段）

整体流程和资料更新一样：
1. 查用户存在
2. 构建只有 `id` + `avatar` 的 patch 对象
3. 写数据库
4. 回读最新快照
5. 转成 `ProfileResponse` 返回

### [18] 到这里，个人资料管理终于完整闭环了

**资料更新流程 PATCH /api/v1/profile：**
1. Controller 接住 PATCH 请求
2. Spring 自动校验 `ProfilePatchRequest` 字段格式
3. 从 JWT 提取 userId（防越权）
4. `ProfileServiceImpl.updateProfile()` 查用户存在
5. 校验至少提交一个字段
6. 如果改了知光号，校验唯一性（排除自己）
7. `getUser()` 构建只含非空字段的 patch 对象（trim/大写标准化）
8. `userMapper.updateProfile(patch)` 动态 SQL 只更新提交的列
9. 回读最新快照
10. `toResponse()` 过滤敏感字段，返回 `ProfileResponse`

**头像上传流程 POST /api/v1/profile/avatar：**
1. Controller 接住 multipart 文件上传
2. 从 JWT 提取 userId
3. `OssStorageService.uploadAvatar()` 上传文件到阿里云 OSS → 返回 URL
4. `ProfileServiceImpl.updateAvatar()` 把 URL 写入 `users.avatar` 字段
5. 回读最新快照，返回包含新头像的 `ProfileResponse`

这样你就知道"为什么资料更新不会覆盖未提交字段"、"为什么知光号校验要排除自己"、"为什么更新后还要再查一次数据库"都不是随机决定，而是有明确的设计意图。

## 六、常见面试题/易错点

### Q1: 为什么用 PATCH 而不是 PUT？

**A**: PATCH 是部分更新，用户只提交想改的字段。PUT 是全量替换，需要传所有字段。用 PATCH 对用户更友好，不需要先查出当前资料再全部提交。

### Q2: 为什么更新后还要再查一次数据库？

**A**: MyBatis 的 `updateProfile` 不会回填更新后的完整实体，且数据库可能有自动更新的时间戳字段。"写后回读"确保返回给前端的数据 100% 是最新状态。

### Q3: 为什么知光号校验要排除自己？

**A**: 用户可能只是改了昵称但没改 zgId。如果不排除自己，每次更新资料都会报"知光号已存在"。`existsByZgIdExceptId(zgId, currentId)` 的 SQL 是 `WHERE zg_id = ? AND id != ?`。

### Q4: 为什么 getUser() 是 static 方法？

**A**: 因为它不依赖任何实例成员，纯数据转换。static 方法调用不需要 this，更高效。这也是一个"代码味道"——如果一个方法不需要访问实例状态，就应该声明为 static。

### Q5: 为什么不直接把 User 实体返回给前端？

**A**: User 包含 `passwordHash` 等敏感字段。直接返回会泄露安全信息。`toResponse()` 做"实体到 DTO"的映射，是分层架构的标准做法。

### Q6: 头像上传每次新建 OSS 客户端，性能会不会有问题？

**A**: 对于低频操作（头像不常换）没问题。但如果上传量大，可以考虑用连接池复用 OSS 客户端，或者使用 Spring 的 `@Bean` 单例管理。
