## 三、模块概览

### 模块一：Canal + Outbox 事件管道

**为什么先做？** 它是事件驱动架构的骨架，搜索模块的增量索引依赖它。

**数据流**：
```
RelationServiceImpl.follow/unfollow()
  -> @Transactional: DB write + outboxMapper.insert()
    -> MySQL binlog
      -> Canal Server
        -> CanalKafkaBridge [Kafka: "canal-outbox"]
          -> CanalOutboxConsumer [relation-outbox-consumer]
            -> RelationEventProcessor [dedup, DB, cache, counters]
          -> CanalOutboxConsumerSearch [search-index-consumer]
            -> SearchIndexService [ES upsert]
```

**任务清单**：
1. 修复 OutboxMapper.xml 缺失的 insert SQL（10 分钟）
2. 实现 OutboxMessageUtil（30 分钟）
3. 创建 OutboxTopics 常量（10 分钟）
4. 实现 CanalKafkaBridge（2 小时）
5. 实现 CanalOutboxConsumer（1 小时）
6. 实现 RelationEventProcessor（1.5 小时）

## 四、关键踩坑点

| 模块 | 踩坑点 | 解决方案 |
|------|--------|----------|
| Canal | filter 表达式格式 `zg_auth\.outbox` | 用反斜杠转义点号 |
| Canal | SmartLifecycle 的 Bean 名称 | 使用 `@Qualifier("threadPoolTaskExecutor")` |
| Canal | follower 表字段顺序 | `to_user_id` 在前，`from_user_id` 在后 |
| AI | DeepSeek 的 maxTokens 设置 | 需要通过 `DeepSeekChatOptions` 设置 |
| AI | RelationEvent getter 方法 | 使用 `getType()` 而不是 `type()`（JavaBean vs record）|
| RAG | VectorStore 返回所有帖子的 chunks | 后过滤：只保留当前 postId 的 chunks |
| RAG | fetchK vs topK | `fetchK = topK * 3`，宽召回再后过滤 |
| 搜索 | ES 的 completion_suggest | 需要特殊的 `type: "completion"` mapping |
| 搜索 | 启动时全量回填 | `@PostConstruct` + 条件检查（索引为空才回填）|
