## 一、核心逻辑总览

### 双令牌机制是什么？

用户登录后拿到**两个令牌**：

| 令牌 | 有效期 | 用途 | 存储 |
|------|--------|------|------|
| **Access Token** | 15 分钟 | 每次 API 请求携带在 `Authorization: Bearer` 头 | 客户端内存 |
| **Refresh Token** | 7 天 | 仅用于调用 `/token/refresh` 换取新的令牌对 | Redis 白名单 |

### 为什么要双令牌？

1. **Access Token 无状态**：RS256 签名验证无需查数据库/Redis，每次请求极快
2. **Refresh Token 可控**：存 Redis 白名单，可随时撤销（登出、改密码、封号）
3. **Token Rotation（轮换）**：每次 refresh 后旧的 refresh token 立即失效，防止重放攻击
4. **短命 Access Token**：即使泄露，15 分钟后自动过期

### 核心流程图

```
注册/登录 ──→ 签发 Access(15m) + Refresh(7d)
                 ↓                     ↓
            Access Token          Refresh Token → 写入 Redis 白名单
                 ↓
        每次 API 请求 → Spring Security 自动验签 (RS256 公钥) → 放行/401

Access Token 过期 ──→ 客户端发 Refresh Token 到 /token/refresh
                 ↓
            1. 解码 Refresh Token → 验证 token_type="refresh"
            2. 查 Redis 白名单 → 确认未被撤销
            3. 签发新的 Access + Refresh
            4. 撤销旧 Refresh Token（轮换）
            5. 写入新 Refresh Token 到 Redis

登出 ──→ 从 Redis 白名单删除对应 Refresh Token
改密 ──→ revokeAll(userId) → 所有 Refresh Token 失效，强制全端下线
```

## 三、按执行流程学习（方法级别详解）

### 流程 1：注册流程

```
客户端 POST /api/v1/auth/register
    ↓
[1] AuthController.register()
    ├─ 解析 HttpServletRequest → ClientInfo(IP, UA)
    └─ 调用 AuthService.register(request, clientInfo)
        ↓
[2] AuthService.register()
    ├─ ① 检查是否同意协议
    ├─ ② 校验标识格式（手机号/邮箱正则）
    ├─ ③ 检查标识是否已存在 → IDENTIFIER_EXISTS
    ├─ ④ 校验验证码 → VerificationService.verify()
    │   └─ Redis Hash: auth:code:{scene}:{identifier}
    │       fields: code, maxAttempts, attempts
    ├─ ⑤ 构建 User 对象（nickname="知光用户"+8位UUID）
    ├─ ⑥ 如有密码 → validatePassword() → BCrypt 编码
    ├─ ⑦ userService.createUser(user) → 写 MySQL
    ├─ ⑧ jwtService.issueTokenPair(user) → ★ 签发双令牌
    │   ├─ Access Token: 15min, claims: {uid, token_type="access", nickname}
    │   └─ Refresh Token: 7d, claims: {uid, token_type="refresh", ...}
    │       jti = UUID.randomUUID() → 这个 ID 用作白名单键
    ├─ ⑨ storeRefreshToken(userId, jti) → 写入 Redis
    │   └─ Redis Key: auth:rt:{userId}:{jti} = "1", TTL=7d
    ├─ ⑩ loginLogService.record() → 写审计日志
    └─ ⑪ 返回 AuthResponse(user + tokens)
```

这一次学习的规则是：
- **流程图只负责让你先看到全貌**。
- **下面正式教学时，按 ①②③ 顺序讲。**
- **某个方法 / 类第一次出现，我就立刻讲透。**
- **不跳过嵌套调用，不让你知识断层。**

#### 第 0 步：先看入口请求长什么样

注册接口接收的请求体不是我凭空写的，它来自 `RegisterRequest`。

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/api/dto/RegisterRequest.java`

```java
public record RegisterRequest(
        @NotNull(message = "账号类型不能为空") IdentifierType identifierType,
        @NotBlank(message = "账号不能为空") String identifier,
        @NotBlank(message = "验证码不能为空") String code,
        String password,
        boolean agreeTerms
) {
}
```

**这里你先必须懂 5 个字段：**
1. `identifierType`：账号类型，只能是手机号或邮箱。
2. `identifier`：真正的账号内容，比如手机号 `13800138000`。
3. `code`：验证码。
4. `password`：密码，可选，所以这里没有 `@NotBlank`。
5. `agreeTerms`：是否同意协议。

**这里的知识点也不能跳过：**
- `@NotNull`：这个字段不能是 `null`
- `@NotBlank`：这个字段不能为空字符串，也不能是只有空格
- `record`：这是 Java 的数据载体，专门用来装请求参数
- `@Valid @RequestBody` 配合它使用时，Spring 会先自动校验，再进入 Controller

所以你看到流程图第一行的：

```java
@Valid @RequestBody RegisterRequest request
```

本质上就是：
1. Spring 先把 JSON 反序列化成 `RegisterRequest`
2. 再检查 `identifierType / identifier / code` 是否满足注解约束
3. 如果不满足，直接 400，压根不会进入业务逻辑

## 第一部分：先把 Controller 入口讲透

### [1] AuthController.register()

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/api/AuthController.java:70-73`

```java
@PostMapping("/register")
public AuthResponse register(@Valid @RequestBody RegisterRequest request, HttpServletRequest httpRequest) {
    return authService.register(request, resolveClient(httpRequest));
}
```

### 这个方法只做 3 件事

#### 1. 接住 HTTP 请求
`@PostMapping("/register")`

意思是：
- 路径是 `/api/v1/auth/register`
- HTTP 方法必须是 `POST`
- 这是注册接口入口

#### 2. 接住两个参数
- `RegisterRequest request`：注册请求体

这里为什么除了 `request` 还要多拿一个 `httpRequest`？
因为后面要从原始请求里提取：
- IP
- User-Agent

这些信息不是注册表单字段，但审计日志需要。

#### 3. 委托给业务层
```java
return authService.register(request, resolveClient(httpRequest));
```

这一行拆开其实是两步：
1. 先执行 `resolveClient(httpRequest)`
2. 再执行 `authService.register(request, clientInfo)`

所以现在不能往下跳，必须先讲 `resolveClient()`。

### [3] ClientInfo 是什么？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/model/ClientInfo.java`

```java
public record ClientInfo(String ip, String userAgent) {

```

它就是一个很纯粹的数据载体，只装两样东西：

### [4] AuthController.extractClientIp()

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/api/AuthController.java:164-174`

```java
private String extractClientIp(HttpServletRequest request) {
    String forwarded = request.getHeader("X-Forwarded-For");
    if (forwarded != null && !forwarded.isBlank()) {
        return forwarded.split(",")[0].trim();
    }
    String realIp = request.getHeader("X-Real-IP");
    if (realIp != null && !realIp.isBlank()) {
        return realIp.trim();
    }
    return request.getRemoteAddr();
}
```

### 这个方法为什么要这样写？

因为真实线上环境通常不是：

```text
用户浏览器 → 你的 Java 服务
```

而是：

```text
用户浏览器 → Nginx / 网关 / 负载均衡 → 你的 Java 服务
```

这时候：
- `request.getRemoteAddr()` 拿到的可能是代理服务器 IP
- 不是用户真实 IP

所以它按优先级做了 3 层兜底：

#### 第 1 层：`X-Forwarded-For`
```java
String forwarded = request.getHeader("X-Forwarded-For");
if (forwarded != null && !forwarded.isBlank()) {
    return forwarded.split(",")[0].trim();
}
```

这通常是最常见的真实客户端 IP 头。
如果里面有多个 IP，比如：

```text
203.0.113.1, 10.0.0.2, 10.0.0.3
```

第一个才是最初的客户端 IP，所以要：
```java
split(",")[0].trim()
```

#### 第 2 层：`X-Real-IP`
```java
String realIp = request.getHeader("X-Real-IP");
if (realIp != null && !realIp.isBlank()) {
    return realIp.trim();
}
```

有些代理不会传 `X-Forwarded-For`，只传 `X-Real-IP`。

#### 第 3 层：`getRemoteAddr()`
```java
return request.getRemoteAddr();
```

如果前两个头都没有，只能退回连接对端地址。

### 到这里，Controller 入口你应该形成完整理解：
1. 收请求
2. 自动校验 DTO
3. 提取客户端信息
4. 调用业务层

现在才能进入真正的核心：`AuthService.register()`。

## 第二部分：正式拆 AuthService.register()

### [5] AuthService.register() 总体代码

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:101-132`

```java
public AuthResponse register(RegisterRequest request, ClientInfo clientInfo) {
    if (!request.agreeTerms()) {
        throw new BusinessException(ErrorCode.TERMS_NOT_ACCEPTED);
    }
    validateIdentifier(request.identifierType(), request.identifier());
    String identifier = normalizeIdentifier(request.identifierType(), request.identifier());
    if (identifierExists(request.identifierType(), identifier)) {
        throw new BusinessException(ErrorCode.IDENTIFIER_EXISTS);
    }
    ensureVerificationSuccess(verificationService.verify(VerificationScene.REGISTER, identifier, request.code()));

    User user = User.builder()
            .phone(request.identifierType() == IdentifierType.PHONE ? identifier : null)
            .email(request.identifierType() == IdentifierType.EMAIL ? identifier : null)
            .nickname(generateNickname())
            .avatar("https://static.zhiguang.cn/default-avatar.png")
            .bio(null)
            .tagsJson("[]")
            .build();

    if (StringUtils.hasText(request.password())) {
        validatePassword(request.password());
        user.setPasswordHash(passwordEncoder.encode(request.password().trim()));
    }

    userService.createUser(user);
    TokenPair tokenPair = jwtService.issueTokenPair(user);
    storeRefreshToken(user.getId(), tokenPair);
    loginLogService.record(user.getId(), identifier, "REGISTER", clientInfo.ip(), clientInfo.userAgent(), "SUCCESS");

    return new AuthResponse(mapUser(user), mapToken(tokenPair));
}
```

这一个方法看起来不长，但里面嵌套了很多第一次出现的方法。
所以我们必须按顺序拆。

### [6] 第 ① 步：检查是否同意协议

```java
if (!request.agreeTerms()) {
    throw new BusinessException(ErrorCode.TERMS_NOT_ACCEPTED);
}
```

### 为什么第一步先做这个？
因为这是最便宜、最直接的业务规则判断：
- 不用查库
- 不用查 Redis
- 不用做任何复杂逻辑

用户没同意协议，就根本不允许继续注册。

### 这里又出现两个第一次出现的知识点
1. `BusinessException`
2. `ErrorCode.TERMS_NOT_ACCEPTED`

你这里要先记住一个原则：
> `AuthService` 不直接返回 HTTP 状态码，它通过抛业务异常，把错误交给全局异常处理器统一翻译。

这里的意思不是“Java 报错了程序崩了”，而是：
- 业务层主动抛一个受控异常
- 告诉外层：这次注册失败，原因是“未同意协议”

所以这一句本质上是在表达一个业务规则：

```text
不同意协议 = 注册流程立即终止
```

### [7] 第 ② 步：校验标识格式 → `validateIdentifier()`

```java
validateIdentifier(request.identifierType(), request.identifier());
```

这一步也不能跳过。

#### 为什么要先校验格式，而不是先查库？
因为如果格式本身就是错的，比如手机号写成 `123`：
- 查库没有意义
- 查 Redis 没意义
- 验证码校验也没意义

所以正确顺序一定是：
1. 先校验格式
2. 再做后续逻辑

### `validateIdentifier()` 完整代码

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:277-284`

```java
private void validateIdentifier(IdentifierType type, String identifier) {
    if (type == IdentifierType.PHONE && !IdentifierValidator.isValidPhone(identifier)) {
        throw new BusinessException(ErrorCode.BAD_REQUEST, "手机号格式错误");
    }
    if (type == IdentifierType.EMAIL && !IdentifierValidator.isValidEmail(identifier)) {
        throw new BusinessException(ErrorCode.BAD_REQUEST, "邮箱格式错误");
    }
}
```

### 这段代码拆成 4 步理解

#### 1. 先看 `type`
如果是 `PHONE`，就走手机号校验。
如果是 `EMAIL`，就走邮箱校验。

#### 2. 真正的正则校验不在这里写
这里调用的是：
- `IdentifierValidator.isValidPhone(identifier)`
- `IdentifierValidator.isValidEmail(identifier)`

说明作者把“业务流程控制”和“正则工具逻辑”拆开了。

#### 3. 如果不合法，直接抛业务异常
手机号错：
```java
throw new BusinessException(ErrorCode.BAD_REQUEST, "手机号格式错误")
```

邮箱错：
```java
throw new BusinessException(ErrorCode.BAD_REQUEST, "邮箱格式错误")
```

#### 4. 如果没抛异常，就表示格式通过
这个方法没有返回值，说明它是“守门员方法”：
- 通过了就继续往下走
- 不通过就直接中断流程

那这里又第一次出现了 `IdentifierValidator`，继续讲。

### [8] IdentifierValidator 是怎么做手机号/邮箱校验的？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/util/IdentifierValidator.java`

```java
public final class IdentifierValidator {

    private static final Pattern PHONE_PATTERN = Pattern.compile("^1\\d{10}$");
    private static final Pattern EMAIL_PATTERN = Pattern.compile("^[A-Z0-9._%+-]+@[A-Z0-9.-]+\\.[A-Z]{2,}$", Pattern.CASE_INSENSITIVE);

    private IdentifierValidator() {
    }

    public static boolean isValidPhone(String phone) {
        return phone != null && PHONE_PATTERN.matcher(phone).matches();
    }

    public static boolean isValidEmail(String email) {
        return email != null && EMAIL_PATTERN.matcher(email).matches();
    }
}
```

### 这里你要抓 3 个重点

#### 1. 为什么这个类是 `final`，构造器还是私有的？
因为它只是工具类：
- 不需要 new
- 不需要继承
- 只提供静态方法

#### 2. 手机号正则：
```java
^1\d{10}$
```
意思是：
- 以 `1` 开头
- 后面必须再跟 10 位数字
- 总长度 11 位

也就是中国大陆手机号的简化校验。

#### 3. 邮箱正则：
```java
^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$
```
再加上：
```java
Pattern.CASE_INSENSITIVE
```

意思是邮箱大小写不敏感。

所以这一步你应该形成这样的认识：
> `validateIdentifier()` 负责决定“什么时候报错”，`IdentifierValidator` 负责决定“什么叫格式合法”。

### [9] 第 ③ 步：标准化标识 → `normalizeIdentifier()`

```java
String identifier = normalizeIdentifier(request.identifierType(), request.identifier());
```

### 为什么格式校验之后，还要做标准化？
因为“格式合法”不代表“存储格式统一”。

例如邮箱：
```text
Test@Example.com
```
和
```text
test@example.com
```

从业务上通常应该视为同一个邮箱。

### `normalizeIdentifier()` 完整代码

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:352-357`

```java
private String normalizeIdentifier(IdentifierType type, String identifier) {
    return switch (type) {
        case PHONE -> identifier.trim();
        case EMAIL -> identifier.trim().toLowerCase(Locale.ROOT);
    };
}
```

### 这一步做了什么？

#### 手机号
```java
identifier.trim()
```
去掉前后空格。

#### 邮箱
```java
identifier.trim().toLowerCase(Locale.ROOT)
```
做两件事：
1. 去掉前后空格
2. 统一转小写

### 为什么要用 `Locale.ROOT`？
因为字符串转小写如果依赖系统默认区域，有时会出现语言环境差异。
`Locale.ROOT` 是最稳妥的“程序内部标准化”写法。

所以这一步的本质是：
> 把用户输入的账号，变成系统内部统一使用的标准格式。

### [10] 第 ④ 步：检查标识是否已存在 → `identifierExists()`

```java
if (identifierExists(request.identifierType(), identifier)) {
    throw new BusinessException(ErrorCode.IDENTIFIER_EXISTS);
}
```

这一步是“防重复注册”。

### 为什么它放在验证码校验之前？
因为如果账号本来就已经注册过：

### [17] 真正的 Redis 校验逻辑：`RedisVerificationCodeStore.verify()`

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/verification/RedisVerificationCodeStore.java:65-92`

```java
@Override
public VerificationCheckResult verify(String scene, String identifier, String code) {
    String key = buildKey(scene, identifier);
    HashOperations<String, String, String> ops = redisTemplate.opsForHash();
    Map<String, String> data = ops.entries(key);
    if (data.isEmpty()) {
        return new VerificationCheckResult(VerificationCodeStatus.NOT_FOUND, 0, 0);
    }
    String storedCode = data.get(FIELD_CODE);
    int maxAttempts = parseInt(data.get(FIELD_MAX_ATTEMPTS), 5);
    int attempts = parseInt(data.get(FIELD_ATTEMPTS), 0);

    if (attempts >= maxAttempts) {
        return new VerificationCheckResult(VerificationCodeStatus.TOO_MANY_ATTEMPTS, attempts, maxAttempts);
    }

    if (Objects.equals(storedCode, code)) {
        redisTemplate.delete(key);
        return new VerificationCheckResult(VerificationCodeStatus.SUCCESS, attempts, maxAttempts);
    }

    int updatedAttempts = attempts + 1;
    ops.put(key, FIELD_ATTEMPTS, String.valueOf(updatedAttempts));
    if (updatedAttempts >= maxAttempts) {
        redisTemplate.expire(key, Duration.ofMinutes(30));
        return new VerificationCheckResult(VerificationCodeStatus.TOO_MANY_ATTEMPTS, updatedAttempts, maxAttempts);
    }
    return new VerificationCheckResult(VerificationCodeStatus.MISMATCH, updatedAttempts, maxAttempts);
}
```

### 这段代码必须按 1~8 步吃透

#### 1. 先拼 Redis key
```java
String key = buildKey(scene, identifier);
```
最终 key 形如：
```text
auth:code:REGISTER:13800138000
```

#### 2. 从 Redis Hash 读出整份验证码记录
```java
Map<String, String> data = ops.entries(key);
```
Hash 里存的是：
- `code`
- `maxAttempts`
- `attempts`

#### 3. 如果整个 key 都不存在
```java
if (data.isEmpty())
```
说明验证码没了：
- 可能根本没发过
- 可能已经过期
- 可能已经成功校验过并删除了

返回：
```java
NOT_FOUND
```

#### 4. 读取验证码和计数信息
```java
String storedCode = data.get(FIELD_CODE);
int maxAttempts = parseInt(...);
int attempts = parseInt(...);
```

#### 5. 如果尝试次数已经超限
```java
if (attempts >= maxAttempts)
```
直接返回：
```java
TOO_MANY_ATTEMPTS
```

#### 6. 如果验证码正确
```java
if (Objects.equals(storedCode, code)) {
    redisTemplate.delete(key);
    return SUCCESS;
}
```

这里有个极其重要的安全点：
> **验证成功后立刻删除验证码，防止重放。**

#### 7. 如果验证码错误
```java
int updatedAttempts = attempts + 1;
ops.put(key, FIELD_ATTEMPTS, String.valueOf(updatedAttempts));
```
会把错误次数 +1。

#### 8. 如果这次错误后刚好达到上限
```java
redisTemplate.expire(key, Duration.ofMinutes(30));
return TOO_MANY_ATTEMPTS;
```

意思是：
- 不只是失败
- 还进入“30 分钟锁定期”

所以这段逻辑非常完整：
- 不存在
- 超限
- 成功
- 失败并累加次数
- 达上限后锁定

### [18] `ensureVerificationSuccess()`：把结果翻译成业务异常

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:253-268`

```java
private void ensureVerificationSuccess(VerificationCheckResult result) {
    if (result.isSuccess()) {
        return;
    }
    VerificationCodeStatus status = result.status();
    if (status == VerificationCodeStatus.NOT_FOUND || status == VerificationCodeStatus.EXPIRED) {
        throw new BusinessException(ErrorCode.VERIFICATION_NOT_FOUND);
    }
    if (status == VerificationCodeStatus.MISMATCH) {
        throw new BusinessException(ErrorCode.VERIFICATION_MISMATCH);
    }
    if (status == VerificationCodeStatus.TOO_MANY_ATTEMPTS) {
        throw new BusinessException(ErrorCode.VERIFICATION_TOO_MANY_ATTEMPTS);
    }
    throw new BusinessException(ErrorCode.BAD_REQUEST, "验证码校验失败");
}
```

### 这个方法的角色是什么？
它不是“校验验证码”，而是：
> **把验证码模块内部的状态，翻译成认证业务层能理解的异常。**

也就是做“状态 → 业务错误码”的映射。

映射关系是：
- `NOT_FOUND / EXPIRED` → `VERIFICATION_NOT_FOUND`
- `MISMATCH` → `VERIFICATION_MISMATCH`
- `TOO_MANY_ATTEMPTS` → `VERIFICATION_TOO_MANY_ATTEMPTS`

这样 `AuthService.register()` 就不用直接理解 Redis 验证码模块的所有细节。

### [22] `validatePassword()` 怎么做密码策略校验？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:292-305`

```java
private void validatePassword(String password) {
    if (!StringUtils.hasText(password)) {
        throw new BusinessException(ErrorCode.PASSWORD_POLICY_VIOLATION, "密码不能为空");
    }
    String trimmed = password.trim();
    if (trimmed.length() < authProperties.getPassword().getMinLength()) {
        throw new BusinessException(ErrorCode.PASSWORD_POLICY_VIOLATION, "密码长度至少" + authProperties.getPassword().getMinLength() + "位");
    }
    boolean hasLetter = trimmed.chars().anyMatch(Character::isLetter);
    boolean hasDigit = trimmed.chars().anyMatch(Character::isDigit);
    if (!hasLetter || !hasDigit) {
        throw new BusinessException(ErrorCode.PASSWORD_POLICY_VIOLATION, "密码需包含字母和数字");
    }
}
```

### 这段代码按 4 步理解

#### 1. 密码不能是空
虽然外层已经 `hasText()` 过一次，这里仍然再防守一次。
这属于方法自身的完整性保护。

#### 2. 去前后空格
```java
String trimmed = password.trim();
```

#### 3. 长度必须达到最小值
```java
trimmed.length() < authProperties.getPassword().getMinLength()
```
这里最小长度不是写死的，而是从配置读。

#### 4. 必须同时包含字母和数字
```java
boolean hasLetter = trimmed.chars().anyMatch(Character::isLetter);
boolean hasDigit = trimmed.chars().anyMatch(Character::isDigit);
```

所以密码策略是：
- 非空
- 长度足够
- 至少一个字母
- 至少一个数字

### [23] `passwordEncoder.encode(...)` 为什么不是直接存密码？


这里存的不是原始密码，而是密码哈希。

### [27] `jwtEncoder` / `jwtDecoder` 是从哪里来的？

第一次出现，就顺手补掉，不然后面你会以为它们是“凭空可用”的。

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/config/AuthConfiguration.java`

```java
@Bean
public JwtEncoder jwtEncoder() {
    AuthProperties.Jwt jwtProps = properties.getJwt();
    RSAPrivateKey privateKey = PemUtils.readPrivateKey(jwtProps.getPrivateKey());
    RSAPublicKey publicKey = PemUtils.readPublicKey(jwtProps.getPublicKey());
    RSAKey jwk = new RSAKey.Builder(publicKey)
            .privateKey(privateKey)
            .keyID(jwtProps.getKeyId())
            .build();
    JWKSource<SecurityContext> jwkSource = new ImmutableJWKSet<>(new JWKSet(jwk));
    return new NimbusJwtEncoder(jwkSource);
}

@Bean
public JwtDecoder jwtDecoder() {
    AuthProperties.Jwt jwtProps = properties.getJwt();
    RSAPublicKey publicKey = PemUtils.readPublicKey(jwtProps.getPublicKey());
    return NimbusJwtDecoder.withPublicKey(publicKey).build();
}
```

### 这里你只要建立正确认知

1. `JwtEncoder` 用 **私钥** 签名。
2. `JwtDecoder` 用 **公钥** 验签。
3. 这就是 RS256 非对称签名的核心。
4. 所以 Access Token 可以被 Spring Security 无状态验签，不用每次都查 Redis。

也就是说：
- 签发阶段：后端私钥参与
- 验证阶段：只需要公钥

### [28] `issueTokenPair()` 本体到底做了什么？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/token/JwtService.java:48-57`

```java
public TokenPair issueTokenPair(User user) {
    String refreshTokenId = UUID.randomUUID().toString();
    Instant issuedAt = Instant.now(clock);
    Instant accessExpiresAt = issuedAt.plus(properties.getJwt().getAccessTokenTtl());
    Instant refreshExpiresAt = issuedAt.plus(properties.getJwt().getRefreshTokenTtl());

    String accessToken = encodeToken(user, issuedAt, accessExpiresAt, "access", UUID.randomUUID().toString());
    String refreshToken = encodeRefreshToken(user, issuedAt, refreshExpiresAt, refreshTokenId);
    return new TokenPair(accessToken, accessExpiresAt, refreshToken, refreshExpiresAt, refreshTokenId);
}
```

### 这段代码你必须按 1~7 步理解

#### 1. 先生成 `refreshTokenId`
```java
String refreshTokenId = UUID.randomUUID().toString();
```

这个值非常关键。
它不是随便一个 UUID，而是后面会同时扮演两个角色：
1. Refresh Token 的 `jti`
2. Redis 白名单的 key 尾部

也就是：
> **Refresh Token 能不能继续使用，不是看 token 字符串本身，而是看它的 `jti` 是否还在 Redis 白名单里。**

#### 2. 获取签发时间 `issuedAt`
```java
Instant issuedAt = Instant.now(clock);
```

这就是两个 token 共同的签发时刻。

#### 3. 计算 Access Token 过期时间
```java
Instant accessExpiresAt = issuedAt.plus(properties.getJwt().getAccessTokenTtl());
```

配置里是 15 分钟，所以这里最终效果就是：
```text
accessExpiresAt = issuedAt + 15min
```

#### 4. 计算 Refresh Token 过期时间
```java
Instant refreshExpiresAt = issuedAt.plus(properties.getJwt().getRefreshTokenTtl());
```

配置里是 7 天，所以这里最终效果就是：
```text
refreshExpiresAt = issuedAt + 7d
```

#### 5. 编码 Access Token
```java
String accessToken = encodeToken(user, issuedAt, accessExpiresAt, "access", UUID.randomUUID().toString());
```

注意这里的 `jti` 又重新生成了一个新的 UUID。
说明：
> Access Token 的 `jti` 和 Refresh Token 的 `jti` 不是同一个东西。

Access Token 的 `jti` 只是令牌唯一标识。
它**不参与** Redis 白名单。

#### 6. 编码 Refresh Token
```java
String refreshToken = encodeRefreshToken(user, issuedAt, refreshExpiresAt, refreshTokenId);
```

这里就不重新生成 UUID 了，而是直接把前面那个 `refreshTokenId` 传进去。
所以：
> Refresh Token 的 `jti = refreshTokenId`。

这就是后面能做白名单轮换的基础。

#### 7. 组装 `TokenPair`
```java
return new TokenPair(accessToken, accessExpiresAt, refreshToken, refreshExpiresAt, refreshTokenId);
```

最后返回的不是两个零散字符串，而是一个完整对象。
这样后面：
- 返回给前端时能直接取 token 和过期时间
- 写 Redis 白名单时能直接取 `refreshTokenId`

### [29] `TokenPair` 是什么？

`TokenPair` 在这里第一次出现，必须立刻讲。

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/token/TokenPair.java`

```java

        String refreshToken,
        Instant refreshTokenExpiresAt,
        String refreshTokenId
```

### 它的 5 个字段分别代表什么？

1. `accessToken`

2. `accessTokenExpiresAt`

3. `refreshToken`

4. `refreshTokenExpiresAt`

5. `refreshTokenId`

   - 但服务端非常重要，因为它是 Redis 白名单记录的 key 组成部分

所以你要把 `TokenPair` 理解成：

### [30] `encodeToken()`：Access Token 是怎么编码出来的？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/token/JwtService.java:79-91`

```java
private String encodeToken(User user, Instant issuedAt, Instant expiresAt, String tokenType, String tokenId) {
    JwtClaimsSet claims = JwtClaimsSet.builder()
            .issuer(properties.getJwt().getIssuer())
            .issuedAt(issuedAt)
            .expiresAt(expiresAt)
            .subject(String.valueOf(user.getId()))
            .id(tokenId)
            .claim(CLAIM_TOKEN_TYPE, tokenType)
            .claim(CLAIM_USER_ID, user.getId())
            .claim("nickname", user.getNickname())
            .build();
    return jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue();
}
```

### 这段代码按字段拆开看

#### 1. `issuer`
```java
.issuer(properties.getJwt().getIssuer())
```

也就是 `iss`。
这里值来自配置，默认是：
```text
zhiguang
```

表示这个 token 是谁签发的。

#### 2. `issuedAt`
```java
.issuedAt(issuedAt)
```

也就是 `iat`。
表示签发时间。

#### 3. `expiresAt`
```java
.expiresAt(expiresAt)
```

也就是 `exp`。
表示过期时间。

#### 4. `subject`
```java
.subject(String.valueOf(user.getId()))
```

也就是 `sub`。
这是 JWT / OAuth2 的标准字段。
这里作者把用户 ID 字符串化后放进去。

#### 5. `id`
```java
.id(tokenId)
```

也就是 `jti`。
代表这张 token 自己的唯一 ID。

#### 6. `token_type`
```java
.claim(CLAIM_TOKEN_TYPE, tokenType)
```

这里实际会写成：
```text
token_type = "access"
```

后面系统就是靠这个字段区分：
- 这是 Access Token
- 还是 Refresh Token

#### 7. `uid`
```java
.claim(CLAIM_USER_ID, user.getId())
```

这是项目自定义字段。
它不是 JWT 规范强制要求的，但非常实用。
因为后面业务层想直接拿 long 类型用户 ID，会比去解析 `sub` 更顺手。

#### 8. `nickname`
```java
.claim("nickname", user.getNickname())
```

这个字段只放在 Access Token 里。
它的意义是：
> 某些接口如果只想快速拿当前昵称，可以直接从 token 里拿，而不用每次都查库。

最后：
```java
return jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue();
```

这一步才是真正把 claims 变成 JWT 字符串。
并且底层会用 RSA 私钥完成签名。

### [31] `encodeRefreshToken()`：Refresh Token 又是怎么编码的？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/token/JwtService.java:102-113`

```java
private String encodeRefreshToken(User user, Instant issuedAt, Instant expiresAt, String tokenId) {
    JwtClaimsSet claims = JwtClaimsSet.builder()
            .issuer(properties.getJwt().getIssuer())
            .issuedAt(issuedAt)
            .expiresAt(expiresAt)
            .subject(String.valueOf(user.getId()))
            .id(tokenId)
            .claim(CLAIM_TOKEN_TYPE, "refresh")
            .claim(CLAIM_USER_ID, user.getId())
            .build();
    return jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue();
}
```

### 它和 Access Token 有 3 个关键区别

#### 1. `token_type` 固定是 `refresh`
```java
.claim(CLAIM_TOKEN_TYPE, "refresh")
```

后面刷新接口里会先检查：
```text
token_type == "refresh"
```

如果你拿 Access Token 去调用刷新接口，会被拒绝。

#### 2. 它没有 `nickname` claim
这是刻意设计。
因为 Refresh Token 的用途只有一个：
> 换新令牌。

它不承担给业务接口传递展示信息的任务，所以不需要塞昵称。

#### 3. 它的 `jti` 就是 `refreshTokenId`
```java
.id(tokenId)
```

这里传入的不是一个临时随机 UUID，而是前面 `issueTokenPair()` 里生成的 `refreshTokenId`。

所以你要建立一个非常清晰的等式：

```text
Refresh Token 的 jti
=
TokenPair.refreshTokenId
=
Redis 白名单 key 的最后一段
```

这三个其实是同一个核心标识。

### [33] `AuthService.storeRefreshToken()` 做了什么？

**位置**：`源代码/zhiguang_be/src/main/java/com/tongji/auth/service/AuthService.java:365-371`

```java
private void storeRefreshToken(Long userId, TokenPair tokenPair) {
    Duration ttl = Duration.between(Instant.now(), tokenPair.refreshTokenExpiresAt());
    if (ttl.isNegative()) {
        ttl = Duration.ZERO;
    }
    refreshTokenStore.storeToken(userId, tokenPair.refreshTokenId(), ttl);
}
```

### 这段代码按 3 步理解

#### 1. 先算 Redis TTL
```java
Duration ttl = Duration.between(Instant.now(), tokenPair.refreshTokenExpiresAt());
```

这里没有直接写死 `Duration.ofDays(7)`，而是根据：
- 当前时间 `Instant.now()`
- token 自己的 `refreshTokenExpiresAt`

动态计算剩余有效期。

这样做更严谨。
因为 Redis 里的白名单记录，应该和 JWT 自身过期时间保持一致。

#### 2. 如果 TTL 已经是负数，就归零
```java
if (ttl.isNegative()) {
    ttl = Duration.ZERO;
}
```

这是一个保护动作。
意思是：
- 万一当前时间已经晚于 refresh token 过期时间
- 那就不要再给 Redis 一个负 TTL

#### 3. 把 `refreshTokenId` 存进白名单
```java
refreshTokenStore.storeToken(userId, tokenPair.refreshTokenId(), ttl);
```

注意存的不是整个 refresh token 字符串，而是：
- `userId`
- `refreshTokenId`
- `ttl`

也就是说，Redis 管理的是“刷新令牌身份”，不是整段 JWT 文本。

### [35] Redis key 是怎么拼出来的？

同一个类里还有这个方法：

所以最终 Redis 里的 key 长这样：


### [45] 到这里，注册流程终于完整闭环了

你现在应该能把整个注册流程按顺序复述出来：

1. Controller 接住 `RegisterRequest`
2. 解析 `HttpServletRequest`，提取 `ClientInfo`
3. `AuthService.register()` 检查是否同意协议
4. 校验手机号/邮箱格式
5. 标准化标识文本
6. 检查账号是否已存在
7. 校验验证码并把结果翻译成业务异常
8. 构建 `User` 对象
9. 如有密码，先做密码策略校验，再做 BCrypt 哈希
10. `userService.createUser(user)` 写入 MySQL，并拿到用户 ID

12. `storeRefreshToken(userId, tokenPair)` 把 Refresh Token 的 `jti` 写入 Redis 白名单
13. `loginLogService.record(...)` 记录注册成功审计日志

15. 返回 `AuthResponse(user + token)` 给客户端

到这一步，你对“注册成功为什么会自动登录”就不该再是模糊理解了。
因为你已经能看清楚整条链路：

```text
创建用户
→ 签发双令牌
→ Refresh Token 写入白名单
→ 返回 user + token
```

这才是这个项目里“注册即登录”的完整实现。

### 流程 2：API 请求认证流程（Access Token 验证）

```
客户端 GET /api/v1/auth/me
    Header: Authorization: Bearer <access_token>
    ↓
[1] Spring Security Filter Chain
    ├─ BearerTokenAuthenticationFilter 拦截请求
    ├─ 提取 Bearer Token 字符串
    ├─ 调用 JwtDecoder.decode(token) → ★ RS256 公钥验签
    │   ├─ 验证签名（public.pem）
    │   ├─ 验证过期时间（exp）
    │   ├─ 验证签发者（iss = "zhiguang"）
    │   └─ 失败 → 401 Unauthorized
    └─ 成功 → 将 Jwt 对象注入 SecurityContext
        ↓
[2] AuthController.me(@AuthenticationPrincipal Jwt jwt)
    ├─ jwtService.extractUserId(jwt) → 从 claims["uid"] 取用户 ID
    └─ authService.me(userId) → 查数据库返回用户信息
```

**重点理解**:
- Access Token **不查 Redis**，完全无状态验证（仅靠 RS256 公钥）
- 验证逻辑全部由 Spring Security + Nimbus 框架自动完成
- `@AuthenticationPrincipal Jwt` 是 Spring 自动注入

**配置要求**（AuthConfiguration 中已配置）:

```java
@Bean
public JwtDecoder jwtDecoder() {
    RSAPublicKey publicKey = PemUtils.readPublicKey(jwtProps.getPublicKey());
    return NimbusJwtDecoder.withPublicKey(publicKey).build();
}
```

#### [13] AuthController.me() 方法详解

**位置**: `auth/api/AuthController.java:138-142`


**职责**: 查询当前登录用户信息

### 流程 3：刷新令牌流程（核心 — Token Rotation）★重点★

```
客户端 POST /api/v1/auth/token/refresh
    Body: {"refreshToken": "<refresh_token>"}
    ↓
[1] AuthController.refresh() → AuthService.refresh(request)
    ↓
[2] AuthService.refresh()
    ├─ ① decodeRefreshToken(refreshToken)
    │   └─ jwtService.decode(refreshToken)
    │   └─ 失败（签名错/过期/格式错）→ BusinessException(REFRESH_TOKEN_INVALID)
    │
    ├─ ② 检查 token_type == "refresh"
    │   └─ 如果传来的是 Access Token → 拒绝
    │
    ├─ ③ extract userId + tokenId(jti) from JWT claims
    │   └─ jwtService.extractUserId(jwt)
    │   └─ jwtService.extractTokenId(jwt)3
    │
    ├─ ④ refreshTokenStore.isTokenValid(userId, tokenId)
    │   └─ Redis: GET auth:rt:{userId}:{tokenId}
    │       → 返回 "1" = 有效；null = 已被撤销/过期
    │   └─ 无效 → BusinessException(REFRESH_TOKEN_INVALID)
    │
    ├─ ⑤ 查数据库确认用户仍存在
    │   └─ findUserById(userId)
    │
    ├─ ⑥ ★ jwtService.issueTokenPair(user) → 签发全新的 Access + Refresh
    │
    ├─ ⑦ ★ refreshTokenStore.revokeToken(userId, tokenId) → 删除旧 Refresh Token
    │   └─ Redis: DEL auth:rt:{userId}:{old_jti}
    │   ← 这一步就是 Token Rotation：旧 refresh token 立即失效
    │
    ├─ ⑧ storeRefreshToken(userId, newTokenPair) → 写入新 Refresh Token
    │   └─ Redis: SET auth:rt:{userId}:{new_jti} = "1", TTL=7d
    │
    └─ ⑨ 返回 TokenResponse（新 access + 新 refresh + 过期时间）
```

**Token Rotation 的安全意义**:
```
假设攻击者偷到了 Refresh Token：
1. 正常用户使用它 → server 签发新令牌对，旧 token 失效
2. 攻击者紧接着使用被偷的旧 token → Redis 中已不存在 → 被拒绝
3. 正常用户感知到新 token，攻击者被拦截

但如果攻击者先使用了怎么办？
→ 正常用户 refresh 时发现 token 已被使用 → 触发安全告警（可在此基础上扩展）
```

```java
@Override
public VerificationCheckResult verify(String scene, String identifier, String code) {
    String key = buildKey(scene, identifier);
    HashOperations<String, String, String> ops = redisTemplate.opsForHash();
    Map<String, String> data = ops.entries(key);
    
    // ① 验证码不存在
    if (data.isEmpty()) {
        return new VerificationCheckResult(VerificationCodeStatus.NOT_FOUND, 0, 0);
    }
    
    String storedCode = data.get(FIELD_CODE);
    int maxAttempts = parseInt(data.get(FIELD_MAX_ATTEMPTS), 5);
    int attempts = parseInt(data.get(FIELD_ATTEMPTS), 0);
    
    // ② 尝试次数超限
    if (attempts >= maxAttempts) {
        return new VerificationCheckResult(VerificationCodeStatus.TOO_MANY_ATTEMPTS, attempts, maxAttempts);
    }
    
    // ③ 验证码正确 → 删除记录（防重用）
    if (Objects.equals(storedCode, code)) {
        redisTemplate.delete(key);
        return new VerificationCheckResult(VerificationCodeStatus.SUCCESS, attempts, maxAttempts);
    }
    
    // ④ 验证码错误 → 增加尝试计数
    int updatedAttempts = attempts + 1;
    ops.put(key, FIELD_ATTEMPTS, String.valueOf(updatedAttempts));
    
    // ⑤ 达到最大尝试次数 → 延长过期时间到 30 分钟（防暴力破解）
    if (updatedAttempts >= maxAttempts) {
        redisTemplate.expire(key, Duration.ofMinutes(30));
        return new VerificationCheckResult(VerificationCodeStatus.TOO_MANY_ATTEMPTS, updatedAttempts, maxAttempts);
    }
    
    return new VerificationCheckResult(VerificationCodeStatus.MISMATCH, updatedAttempts, maxAttempts);
}
```

- ✅ 整个方法（28 行）

**安全设计**:
- 验证成功后**立即删除**验证码（防重用）
- 尝试失败达上限后，锁定 30 分钟（防暴力破解）

## 九、常见面试题/易错点

### Q1: 为什么 Access Token 不存 Redis 而 Refresh Token 要存？

**A**: Access Token 每次请求都要验证，存 Redis 会增加网络开销。RS256 公钥验签是纯本地计算，极快。Refresh Token 只在 refresh 时使用（7 天才一次），存 Redis 可控撤销，性能影响可忽略。

### Q2: Token Rotation 中，为什么要先 revoke 旧 token 再 store 新 token？

**A**: 顺序不是关键——关键是**旧 token 必须失效**。代码中是先 `revokeToken(old)` 再 `storeRefreshToken(new)`，即使中间抛异常，旧 token 已删除，新 token 未写入，客户端拿不到新 token 但可以再次 refresh（只要有备份机制）。

### Q3: 如果 Refresh Token 泄露了怎么办？

**A**: Token Rotation 机制下，正常用户下一次 refresh 会使旧 token 失效。但如果攻击者先使用了，正常用户的 refresh 会被拒绝。可以在此基础上扩展：检测到"已使用过的 refresh token"再次出现时触发安全告警。

### Q4: 改密码为什么要 revokeAll？

**A**: 改密码通常意味着用户怀疑账号被盗。`revokeAll(userId)` 使用 Redis `KEYS auth:rt:{userId}:*` 找到所有设备的 Refresh Token 并批量删除，强制所有端重新登录。

### Q5: `Clock clock = Clock.systemUTC()` 为什么要用字段而不是直接 `Instant.now()`？

**A**: **可测试性**。测试时可以注入 `Clock.fixed()` 来控制"当前时间"，从而精确测试 token 过期行为，无需等待真实时间流逝。这是依赖注入的最佳实践。

### Q6: 为什么 `decodeRefreshTokenSafely` 返回 `Optional` 而不是抛异常？

**A**: 登出是"尽力而为"的操作。用户可能在 token 过期很久后才点"退出"，此时不应该因为 token 无效而返回 400 错误。使用 `Optional` 可以让失败的情况静默处理。
